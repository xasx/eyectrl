# EyeCtrl Architecture Assessment — 2026-08-10

> Evidence-based assessment. All facts verified against the **live codebase and current GitNexus graph**
> (`eyectrl`: 11,768 symbols / 27,754 edges / 300 flows, index 5 commits behind HEAD) and the
> **csproj-level dependency graph** (authoritative for layering), not the older narrative docs.
> Generated by request after a `thorough architecture assessment`.

## Verdict

**A well-layered, actively-maintained gaze-control platform with sound foundational invariants that
are enforced *only* by convention. The layering is clean and acyclic; the chief debts are two runaway
god-objects in the App layer and the absence of any automated guard for the very invariants the
project prides itself on.** No correctness, safety, or security regression is indicated today; the
risks are maintainability of the coordination core and thin coverage on the public SDK surface.

## 2. Strengths (evidence-backed)

1. **Clean, acyclic layering with a real foundation.** Core is dependency-free; `ViewModels → Core`
   never touches `Platform`; the SDK chain (`Contracts → Abstractions → Sdk.Wpf/WinUI`) is fully
   isolated and talks to App only over the `eyectrl_dwell` named pipe. Zero import cycles.
2. **Well-chosen seams for hard problems.** `ILanguageModelPredictor` keeps ONNX out of Core
   (invariant #8); `IGazeProvider` abstracts Tobii-vs-mouse with a graceful conditional build
   (`TOBII_AVAILABLE`); `IInputSimulator` isolates `SendInput`. The **Supervisor is a separate
   process** (invariant #10) — resilience is decoupled from the thing it guards.
3. **Settings validation is genuinely robust.** `IValidatable` + `ValidationHelper`, defense-in-depth
   on load (fall back to defaults) and save (throw), backed by 84+ property-validation tests
   (`docs/ARCHITECTURAL_VALIDATION_SYSTEM.md`).
4. **Fault containment on the hot path.** Gaze observer fan-out uses copy-on-write handler arrays
   with per-observer `try/catch` + `HandlerFaultReporter` rate-limiting — a buggy/throwing observer
   cannot take down the gaze thread.
5. **Real CI quality gates.** Build + `Category!=UI` tests + benchmark generator tests + **coverage
   threshold (line ≥ 50%, branch ≥ 45%)** + a Python palette validator (10 WCAG/CIEDE2000/dichromat
   gates) that runs *before* the build. Coverage is being actively driven upward.
6. **Test concentration where it matters.** `Core.Tests` (15.6k lines) and `App.Tests` (11.7k)
   dominate — the domain and composition layers are the most exercised.

## 3. Concerns (prioritized)

### 🔴 P1 — `EventCoordinator.cs` is a runaway god-object (1,654 lines, 32 handlers)

The March 2026 review (`docs/ARCHITECTURE_ISSUES_SUMMARY.md`) tracked `App.xaml.cs` as the god-object
(Issue #1). That was fixed — `App.xaml.cs` shrank **771 → 709 → 541**. But the gravity migrated:
`EventCoordinator` is now the **largest file in the codebase**, wiring ~8 view models plus drag,
quick-actions, media, window-actions, keyboard, emoji, prediction, calibration, and settings through
**32 distinct `Handle*/On*` methods**. The old review never flagged it. This is the single biggest
maintainability debt today. A concrete decomposition plan is in
[`docs/EVENTCOORDINATOR_DECOMPOSITION_PLAN.md`](./EVENTCOORDINATOR_DECOMPOSITION_PLAN.md).

### 🔴 P1 — `SettingsWindow.xaml.cs` grew, didn't shrink (1,630 lines, still imperative)

March Issue #9 ("large procedural window, no MVVM", then 1,004 lines, "5–7 days to fix") is **open
and larger** — 1,630 lines of code-behind with magic-number constants (`ControlBtnRadius=50`,
`ColorSwatchRadius=35`, `TabBtnRadius=85`, …). The hotspot map has *inverted* since the last review:
the two biggest files are now `EventCoordinator` and `SettingsWindow`, both > 1.6k lines.

### 🟡 P2 — The 11 architectural invariants are documented, not enforced

There is **no layering test anywhere** — no NetArchTest / ArchUnitNET / BannedApiAnalyzers
(grep-confirmed across all `*.csproj`/`*.props`). The invariants in `ARCHITECTURE.md §7` ("Core never
references Platform", "Supervisor never references App", "ViewModels never references Platform") hold
*today* only because the csproj graph happens to encode them and reviewers happen to catch
regressions. A single ill-advised `<ProjectReference>` addition would silently violate them. The doc
named `ARCHITECTURAL_VALIDATION_SYSTEM.md` is **misleadingly named** — it validates *settings values*,
not architecture.

> **Addressed by this assessment cycle:** a new automated layering test was added — see
> [`tests/EyeCtrl.Architecture.Tests`](../tests/EyeCtrl.Architecture.Tests/). It encodes the csproj /
> assembly-reference rules as a CI gate.

### 🟡 P2 — Public SDK surface is thinly tested

`Sdk.Wpf.Tests` = 79 lines, `Sdk.WinUI.Tests` = 28 lines, `Sdk.Abstractions.Tests` = 213 lines. This
is the **third-party integration boundary** (the thing external apps depend on for gaze-dwell), and
the named-pipe protocol (`WireMessages`, `DwellClient`, `OutboundRectTracker`) deserves contract-level
coverage. High blast-radius, low coverage.

### 🟡 P2 — Named-pipe IPC flakiness (known, documented)

`eyectrl_watch` / `eyectrl_dwell` tests flake and hang under contention because pipe names are
machine-global; issue #76 is open. `AGENTS.md` correctly prescribes GUID-suffixed test pipe names and
the pattern is followed — but it is a class of fragility that will recur with every new pipe-using
service.

### 🟢 P3 — Two TFM islands

`net8.0` (Contracts / SDK) vs `net10.0` (everything else) is intentional (third-party consumers may be
on `net8`), but it means the SDK chain cannot use C# 14 / `net10` features and is a constraint every
Contracts/SDK change must weigh. Worth a one-line note in `AGENTS.md` (currently absent).

## 5. CI / enforcement posture

- Build + `Category!=UI` tests run on `push` to `main` and on PRs targeting `main` (blocking).
- Coverage is collected and gated: **line ≥ 50%, branch ≥ 45%** (`ci.yml`).
- A pre-build **palette validator** (`tools/palette_validate.py`) enforces contrast/legibility across
  themes — an unusually mature accessibility gate.
- UI tests (FlaUI, `Category=UI`) are **not** run in CI (need an interactive desktop); run locally.
- **No layering/architecture test existed prior to this assessment** — see recommendation #1.

## 6. Recommendations (ordered by value / risk)

1. **Automated layering test** (P2, ~0.5 day) — *done this cycle*
   (`tests/EyeCtrl.Architecture.Tests`). Converts the csproj-level invariants from convention into a
   CI gate. Extend it over time with namespace-level rules.
2. **Decompose `EventCoordinator`** (P1) — split the 32 handlers into focused coordinators
   (`OverlayBindingCoordinator`, `DragCoordinator`, `QuickActionsCoordinator`, `KeyboardCoordinator`,
   `InputActionDispatcher`, `SettingsUiCoordinator`, `ToolbarLifecycleCoordinator`) behind a thin
   orchestrator. Full plan:
   [`docs/EVENTCOORDINATOR_DECOMPOSITION_PLAN.md`](./EVENTCOORDINATOR_DECOMPOSITION_PLAN.md).
3. **Re-MVVM `SettingsWindow`** (P1, carry-over). The magic-number consts and code-behind construction
   are the March Issue #9, now worse. Even partial extraction of the `Build*Pages` construction into
   VM-bound templates would help.
4. **Raise SDK-layer test coverage** (P2): contract tests for the `eyectrl_dwell` wire protocol
   (register / update / unregister / activated, rect dedup, reconnect), against GUID-suffixed pipe
   names per `AGENTS.md`.
5. **Refresh the docs**: add the 6 missing projects + TFM note to `AGENTS.md`; regenerate
   `ARCHITECTURE.md` from the live graph (`node .gitnexus/run.cjs analyze`, then regenerate); mark or
   retire the March issues summary.
6. **Close the loop on issue #76** (pipe-name contention) — consider a per-test-process pipe namespace
   or a shared test pipe broker so the fragility stops recurring with each new pipe service.
