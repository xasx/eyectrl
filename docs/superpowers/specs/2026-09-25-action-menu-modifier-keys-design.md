## Problem

Every mouse action EyeCtrl simulates is bare. `IInputSimulator`'s click and wheel methods carry no modifier state, the ring's `InteractionAction` has no modifier dimension, and a gaze-only user therefore cannot perform any of the ordinary held-modifier gestures a physical-mouse user does without thinking: Shift+click (range select), Ctrl+click (multi-select, open-in-new-tab), Alt+click (per-app semantics), Ctrl+wheel (browser zoom, Explorer icon scale). The keyboard half of this already exists — `ModifierKey` (`src/EyeCtrl.Core/Keyboard/ModifierKey.cs`), the keyboard's latched modifiers (`KeyboardViewModel.cs:68` field, `:70` copy-on-read property), atomic modified key sequences (`Win32InputSimulator.BuildModifiedKeySequence`) — but nothing connects it to the mouse path, and no UI offers a mouse modifier while the action menu is open.

Display and owner context: 3840×2400 physical at 200% = **1920×1200 DIP** (probed). Owner settings (read-only): `viewPosition: atCenter`, **`selectionMode: manualSelection`** (menu opens via the manual path: activation dwell → zoom view → precise dwell → menu), `keySizeMultiplier: 1.5`, toolbar Top-docked, `adaptation.enabled: false`. Margin arithmetic (round-4 F7 resolution): `GeometryMaxMarginPx` is a **0–300 user setting** (`AdaptationSettings.cs:84–85`), the effective margin is fraction × base clamped to it (`GeometryRouter.cs:55–56`), and the owner's `geometryBiggerMaxFraction` 0.5 binds first — mod buttons ≤ 50 px, ring items ≤ 70 px; the mod bar's absolute worst case is 100 px because fractions cap at 1.0. The owner's rings are SIX slots on both layers (manual path adds Back to 4 primary actions, and 5 secondary actions + BackToPrimary) — neighbour gap 115 DIP (`ActionMenuSettings.cs:36`). Ring geometry: effectiveRingRadius 255 DIP, menu-center clamp 325 DIP (`ActionMenuLayoutHelper.cs:32–35`); edge-button centers inset 30 + 50 + 10 = 90 DIP from an edge, radius `UIConstants.ButtonRadius` = 50; mod-button centers 240 px physical apart, base radius 100 px.

## Behavior

While the action menu is open (normal and manual-selection path alike), the LEFT screen edge shows three dwell buttons — **Shift, Ctrl, Alt, top to bottom** — mirroring the right-edge Close/Help pair:

- Dwell a button → that modifier **latches** for the current menu session (visual latched state). Dwell it again → unlatches. Multiple modifiers can latch at once (Ctrl+Shift+click).
- **Re-arm rule (round-1 blocker fix; round-3 gate; round-4 refinement):** after a toggle activation, the bar VM tracks a pending re-arm FOR THAT BUTTON ID (pendings are per-id — toggling Ctrl while Shift's re-arm is still pending must not disturb Shift's). While a re-arm is pending AND the pending target is the **nearest hitting target** (the target the detector itself would select), the VM skips `DwellDetector.Update` for the bar. A pending clears only after gaze has stayed outside that target's effective hit region **continuously for D = 150 ms** (the `MaxCreditedSampleGapUs` precedent; owner-vetoable — ledger L6). Net contract: a mod button **toggles once per gaze entry** — a held gaze cannot re-toggle it, a one-sample flicker outward cannot either, and a sustained exit followed by a return is a deliberate second toggle.
- **Refusal is structural (round-3 F3):** while the latch is non-empty, Drag and ScrollMode are **not dwell targets at all** — `BuildLayer` skips their `AddTarget` (slot angles preserved: the step still divides by the full item count), so their arcs never fill, no activation fires, no completion cue plays, and no `Activated` outcome reaches the struggle sink. The slot still renders, **dimmed** via a per-button child-canvas group opacity (mechanism 9) — a disabled control that does not pretend to work. The `OnTargetActivated` refusal branch stays as a defensive backstop only.
- Picking a ring action sends the latched set with the selection. The simulated input is **one atomic SendInput batch** per click: modifier key-down(s) → the mouse down/up event(s) → modifier key-up(s) in reverse. DoubleClick is ONE batch (mods↓, down, up, down, up, mods↑) — the exact event shape a physical user produces. When Alt is in the set, an unassigned menu-mask key (VK `0xE8`, the AutoHotkey `#MenuMaskKey` precedent) is injected down+up immediately before the Alt key-up. A modified wheel batch leads with a MOVE|ABSOLUTE event: wheel events alone land at the current cursor, and `ResetToFreeLook` re-enables the per-frame gaze `MoveCursor` across a doubly-deferred dispatch (`Win32InputSimulator.cs:85–87`, `GazeEngine.cs:597–601`).
- **Partial-send compensation (best-effort, stated honestly):** the send path observes the injected count; when 0 < sent < count, compensating events are sent — a mouse-up for each unmatched mouse-down (BEFORE the modifier ups), the mask pair before a compensating Alt-up, and key-ups for modifiers whose down landed AND whose up did not (including a landed-but-unmatched mask down). A fully blocked batch (UIPI, sent = 0) injects nothing and needs none. A compensation failure gets its OWN log line — `SendRaw`'s 30 s rate limit (`:295–296`) would otherwise suppress it milliseconds after the partial-send warning. The design goal is "a partial send cannot silently weld modifiers down", not an absolute guarantee.
- Applies to the click family (Left/Right/Middle/Double) and the one-shot scroll family (Up/Down/Left/Right). **Modified scrolls send ONE wheel notch** — the four arms map to (0,+1), (0,−1), (−1,0), (+1,0) with delta 1 when modified (ledger L9, with the owner-cost statement and its caveats below).
- **One-shot lifecycle:** the latch exists only for the current menu opening — reset on every show BEFORE `BuildLayer()` reads it for the dim state, cleared on hide, toggles ignored while the menu is hidden (the coordinator's hide is deferred twice, `OverlayMessageCoordinator.cs:158`, while the VM's reset runs synchronously). It survives More/BackToPrimary layer switches (`BuildLayer` re-reads the latch each rebuild — pinned by test).

**Known geometry limits (recorded; follow-ups, not v1 work):** under AtGaze a ring item can overlap the mod buttons — center-to-center distances of ~7.5–42 DIP mean the circles overlap by up to ~80 DIP against radii 70 + 50; the shipped right bar has the same defect today. A menu opened over a visible keyboard puts the lower mod button near the keyboard's bottom-left keys — reachable for this owner (bottom-docked keyboard at the 75%-height anchor, 1.5× keys) INDEPENDENT of ViewPosition. A LEFT-docked toolbar (`ToolbarSettings.DockedEdge` supports Left, 120-DIP band) would sit directly under the mod bar; the owner docks Top. All three belong to one geometry pass (see Geometry limits). Within the ring: neighbour capture of a dimmed slot's drawn disc requires margin > chord − 140 px. At the owner's SIX slots (chord 115 DIP) that is > 230 px physical — impossible (the ring's margin is fraction-capped at ≤ 140 px). It becomes reachable on a nine-slot secondary layer at margin > 34 DIP = 69 px, which the owner's current 0.5 × 140 = 70 px bound just exceeds (round-4 F6 — stated with the bound, not as a blanket "pre-existing").

## Mechanism

1. **Core — pass-through only** (`src/EyeCtrl.Core/Processing/InteractionManager.cs`): `OnActionSelected(InteractionAction action, IReadOnlySet<ModifierKey>? modifiers = null)`; the `ActionRequested` event gains the same trailing parameter. Core stores nothing and branches on nothing. BOTH raise sites pass it: the action-menu path (`:224`) forwards the parameter; the repeat-mode tick (`:362`) passes `null` (Core test pins that repeat ticks carry no modifiers). Production blast radius: one caller (`GazeEngineAdapter.cs:107`), one subscriber (`GazeEngineAdapter.cs:63`); the 15 test-subscriber lambdas across 6 files gain the third parameter (census verified exact by round 1).

2. **Messages** (`src/EyeCtrl.ViewModels/Messages/InteractionMessages.cs`): `ActionSelectedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`; new `ToggleActionMenuModifierMessage(ModifierKey Modifier)`; `ActionRequestedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`.

3. **The latch lives in `ActionMenuViewModel`**, mirroring the keyboard's precedent:
   - `Receive(ToggleActionMenuModifierMessage)` toggles and raises — **only when `IsVisible`**; a toggle deferred past a hide lands on a closed menu and is dropped.
   - `Receive(ShowActionMenuMessage)` resets the latch **before** `BuildLayer()` (which reads it for the dim state); `Receive(HideActionMenuMessage)` clears it.
   - **Capture means COPY:** `OnTargetActivated` snapshots `new HashSet<ModifierKey>(backing)` into the `ActionSelectedMessage` (the `KeyboardViewModel.cs:70` copy-on-read precedent). The hide is queued ahead of the action message (`InteractionManager.cs:213` vs `GazeEngineAdapter.cs:279–280`/`:334`), so an aliased set really would arrive empty.
   - **Dimmed = not a target:** `BuildLayer` computes every slot's position (angle step over the FULL item count, so geometry never shifts) but skips `DwellDetector.AddTarget` for items whose action is Drag/ScrollMode while the latch is non-empty; each item VM carries an immutable `IsDisabled` flag for the render. On a latch empty↔non-empty crossing the VM calls `BuildLayer()` (which re-reads the latch and bumps `RingVersion` LAST, per the pinned ordering at `:151`) — the coordinator's existing `RingVersion` branch then redraws from the freshly rebuilt `Items`; a bare `RingVersion++` would redraw stale items and never dim (round-3 F2).
   - **Backstop refusal:** `OnTargetActivated` for Drag/ScrollMode with a non-empty latch sends nothing and returns — unreachable while dimmed items have no target, kept as a guard against ordering surprises.

4. **Input layer** (`src/EyeCtrl.Core/Interfaces/IInputSimulator.cs`, `src/EyeCtrl.Platform/Input/Win32InputSimulator.cs`):
   - New default-interface-method overloads `LeftClick/RightClick/MiddleClick/DoubleClick(PhysicalPoint, IReadOnlySet<ModifierKey>?)` and `Scroll(PhysicalPoint, int, int, IReadOnlySet<ModifierKey>?)`, default bodies throwing `NotSupportedException` (the `MiddleClick` precedent, `IInputSimulator.cs:30`) — existing fakes compile; a fake that actually receives a modified call fails loudly.
   - **Pure seam, characterization scoped to the real gap:** the wrapping is a new internal static pure builder `WrapWithModifiers(IReadOnlySet<ModifierKey>?, INPUT[] body)` — downs in `BuildModifiedKeySequence`'s order (Ctrl, Alt, Win, Shift; only Shift/Ctrl/Alt arrive), body, ups reversed, plus the Alt mask pair. Two `BuildModifiedKeySequence` tests exist (`Win32InputSimulatorClampTests.cs:37` no-modifier shape, `:49` Ctrl+Shift order/reversed-ups); characterization extends coverage to **Alt, the Win extended flag, and extended main keys** BEFORE the extraction.
   - `SendRaw` gains an `int` return (the injected count; it remains the per-frame `MoveCursor` path — a return value costs nothing there). The new mouse overloads compose `WrapWithModifiers` output and send through `SendRaw`; on `0 < sent < count` the Behavior-paragraph compensation is issued, and a compensation send failure is logged on its OWN line, not through the rate-limited path. `SendModifiedKeyPress` (direct `NativeMethods.SendInput` today, `:155`) adopts the same `SendRaw` + compensation path — **this changes the shipped keyboard send path, so Task 1 carries keyboard regression coverage**.
   - `DoubleClick(pt, mods)` = ONE batch (down, up, down, up between the modifier pair). Null/empty modifiers ⇒ exactly the current byte stream — including `Scroll`'s two separate `SendInput` calls for the X/Y legs (`:84–95`) and the unmodified wheel's lack of a leading MOVE (pre-existing; follow-up 4).

5. **Dispatch** (`src/EyeCtrl.App/Services/Coordinators/KeyboardInteractionDispatcher.cs:143`): explicit routing — `mods is { Count: > 0 } ? simulator.X(pt, mods) : simulator.X(pt)`; the four scroll arms map to (0,+1), (0,−1), (−1,0), (+1,0), each with delta 1 on the modified arm (`DefaultScrollAmount = 3` stays unmodified). Never a blind nullable pass: with null it must behave byte-identically AND `TestFakes.FakeInputSimulator` (`TestFakes.cs:342`) does not implement the overloads. Throwing defaults catch stray calls; only recorded-modifier assertions catch dropped ones (Testing). The `Log.Information` line gains `Modifiers={Modifiers}`.

6. **Left-edge bar — second instance, not a subclass** (`EdgeButtonBarWindow`/`EdgeButtonBarViewModel` reused): the dwell registry is owner-keyed (`DwellDetectorRegistry.Register(object owner, …)`); both routers iterate the registration snapshot without keying by context (`DwellTimeRouter.cs:38`, `GeometryRouter.cs:49`). **DI shape:** the existing unkeyed `AddSingleton<EdgeButtonBarViewModel>()` (`AppBootstrapper.cs:381`, resolved at `:637`) stays as the right bar; exactly ONE keyed singleton is added for the mod bar. `IOverlayManager` gains `IEdgeButtonBar ActionMenuModBar` as a **default interface property whose default throws** — the six fakes keep compiling, and `TestFakes.PartialOverlayManager` (`TestFakes.cs:277`) gains an OPTIONAL mod-bar slot so `HideActionMenuBarOwnershipTests` (built via `MakeOverlayManager`, `:164–168`) can exercise the new paths. The positional `OverlayViewModels` record gains the member at both construction sites (`App.xaml.cs:198`, `AppBootstrapper.cs:627`) and the `ResolveViewModels` tuple (`App.xaml.cs:572–595`); `OverlayManager` builds/binds/wires a second `EdgeButtonBarWindow` exactly like the first (`:112`, `:138–154`).

7. **Definitions** (`src/EyeCtrl.App/Services/ActionMenuModifierButtons.cs`, new): three `EdgeButtonDefinition`s — ids `ActionMenu_mod_Shift` / `ActionMenu_mod_Ctrl` / `ActionMenu_mod_Alt`; `Activate` sends `ToggleActionMenuModifierMessage`; `RadiusLogical = UIConstants.ButtonRadius` (`UIConstants.cs:18`, NOT the ring's `ActionMenuButtonRadius`); labels always shown; dwell = the menu's ring dwell (`ShowBack ? ManualSelectionActionMenuDwellMs : ActionMenuDwellMs`); VerticalOffsets `0, ±(2·ButtonRadius + ManualSelectionSideButtonGap)` (`UIConstants.cs:37`), logical px converted with `DpiHelper.LogicalToPhysicalY` exactly like `ActionMenuEdgeButtons.cs:30–31` (`AddTarget` adds the offset to the anchor in physical space, `EdgeButtonBarViewModel.cs:107`). The definitions FACTORY (latched/unlatched variants per current latch) is shared between the show path and the rebuild path; only the anchor and the `ShowButtons` call are show-path-only.

8. **Show/hide placement (round-2 Finding 2 — fault isolation):** both handlers run inside ONE shared try/catch today (`OverlayMessageCoordinator.cs:116–153`, `:160–189`); a mod-bar fault must not kill the right-bar hide (the strongest safety net in the app — a gaze-only user holding a pressed mouse button with nothing on screen to release it). Therefore: each bar gets its OWN try block, and in BOTH handlers the left bar is handled AFTER the right bar. Show: right-bar `ShowButtons` first (`:131–138`), then the left-bar show — still BEFORE the `ResolvedControl == null` early return at `:140`. Hide: the right-bar ownership-guarded hide first, then the left-bar hide — unconditional (nothing else ever owns the left bar), outside the ownership `if`, inside its own try. Anchor via `ScreenGeometry.LeftEdgeAnchor(...)` — a new mirror of `RightEdgeAnchor` with a pure-arithmetic test overload (`ScreenGeometry.cs:40–51` pattern); inset 30 logical (per-coordinator `RightEdgeInsetLogical` copies at `OverlayMessageCoordinator.cs:28` / `OverlayVmBindingCoordinator.cs:21`; a third on `KeyboardEdgeButtons`, `:30`).

9. **Mod-bar visuals and re-arm (round-1 blocker; rounds 3–4 refinements):**
   - **Binding branch (round-2 F4; round-4 F4/F8):** the `LatchedModifiers` listener is hosted in `OverlayVmBindingCoordinator.OnActionMenuVMPropertyChanged` (`:282–316`). Its try/catch must ENCLOSE the handler's prologue (`:286–288` dereferences `ActionMenu`, `CursorCircle` and `ActivationButton` on EVERY property change, before any branch) — either by wrapping from the top of the handler or by hoisting the branch into its own handler subscribed to the same VM; a branch-local try that starts after the prologue covers nothing. It is a SEPARATE `else if` on `LatchedModifiers`, guarded on `IsVisible` as defense-in-depth (a deferred toggle is already a VM no-op while hidden). Its body: `ReplaceButton` for the ONE toggled id, reached via the bar's `EdgeBarVm` (`IEdgeButtonBar.cs:40` — no new interface member; two implementers stay untouched). A latch empty↔non-empty crossing instead routes through the VM's `BuildLayer()` for the ring dim (mechanism 3); the bar icons still swap via the coordinator branch.
     **Crossing escape (round-4 F8, recorded):** the crossing enters the UNWRAPPED `RingVersion` branch (`:306–315` → `ShowActionMenu`) from inside the bar detector's `Update` — a throw there skips the sink reports (`:418–426`) and later recipients of that sample. This is pre-existing for More/Back via the ring's own Update; the mod bar adds an entry point. Pending is set BEFORE `Activate`, so the button stays gated on a throw (no re-toggle). Accepted for v1 with wrapping the shared `RingVersion` branch filed as a hardening follow-up.
   - `EdgeButtonBarViewModel` gains `ReplaceButton(string id, EdgeButtonDefinition definition)`: swaps the `_definitions` entry (no-op when the id is missing), raises `ButtonSetChanged`, touches NOTHING else — no `ClearTargets`, no `ResetCooldown` (`EdgeButtonBarViewModel.cs:44` is the round-1 blocker), no `Buttons` mutation (`EdgeButtonState` has no icon state, `EdgeButtonState.cs:11–15`; `SyncButtons` re-reads `DefinitionFor(id).Icon`, `EdgeButtonBarWindow.xaml.cs:92–96`). `EdgeButtonDefinition` gains a `RearmOnGazeExit` flag (default false); the mod-bar definitions set it. (The right bar's Help toggle shares the no-re-arm exposure — follow-up 2, a one-flag fix once this lands, with the F1 predicate applying there too since Help's neighbour is Close.)
   - **Re-arm = NEAREST-HITTING GATE (round-3 gate; round-4 F1/F2/F3/F9 refinement):** the detector activates the nearest HITTING target (`DwellDetector.cs:325–345`); mod centers are 240 px apart with base radius 100 px, so at margin > 20 px the pending target's effective circle crosses the neighbour bisector, and at margin > 40 px it covers part of the neighbour's drawn disc — a REGION-membership gate would dead-zone samples the detector would award to the neighbour (at the owner's 50 px bound: Ctrl's facing margin band plus 10 px of drawn disc). So the gate predicate is: skip `DwellDetector.Update` for the bar only while a re-arm is pending AND the pending target is the **nearest hitting target among the VM's retained instances** — i.e. exactly the sample the detector would award to the gated button. When a neighbour is nearest-hitting, updates run normally and the neighbour dwells legitimately. Safety of the skip itself (round-4 audit): when the gate engages, nothing is mid-accumulation — the activation pass cleared every non-nearest target (`:388–409`) and the activated one (`:382–383`); gated samples look like silence (`:285–286`); the first ungated sample re-anchors under the `MaxCreditedSampleGapUs` bound (`:299–306`), so runs of skipped samples can never credit stale time (credited runs < 150 ms, ≥ 150 ms re-anchored — pinned by test).
     - Pending re-arms are tracked PER BUTTON ID, recorded BEFORE `def.Activate(Messenger)` runs — order-independent under gating, and a throwing chain leaves the button gated rather than re-toggleable. Toggling a second button while the first's re-arm is still pending (reachable only in tests — the 150 ms debounce elapses long before another 600 ms dwell can complete) must gate each id independently.
     - The pending state stores IDS and resolves each target instance through the VM's id→instance map (updated in `AddTarget`) ON EACH SAMPLE — a captured instance or geometry snapshot goes stale when the detector replaces an instance via `AddButton(existingId)` (`DwellDetector.cs:112`) and later router applies reach only the snapshot (round-4 F9).
     - **Debounced clear (round-4 F3):** pending clears only after gaze has stayed outside the pending target's effective hit region continuously for **D = 150 ms** (the `MaxCreditedSampleGapUs` precedent; owner-vetoable). A one-sample flicker outward then changes nothing — the round-1 timeline (cooldown expiry, re-fire at ≈T+1000) cannot return; a sustained exit of ≥ D re-arms. Outside samples always update normally, so the debounce does not delay any neighbour.
     - Pending clears in `ShowButtons`, `Hide`, and `RemoveButton(id)` — ONLY that id's entry (round-3 F7). **A `RemoveButton`+`AddButton` implementation of the icon swap is FORBIDDEN (round-4 F2):** the coordinator branch runs synchronously INSIDE the toggle chain, after pending was recorded — its `RemoveButton(id)` would clear the just-recorded pending and re-import the round-1 blocker at ≈T+1000; only the cooldown survives it, so the T+700 discriminator does NOT catch it. The App-level held-gaze assertion (Testing) kills it.
     - **No hysteresis beyond the debounce**; the honest contract is "toggles once per gaze entry".
   - **Latched visual:** three new `ActionIcon` values (Shift, Ctrl, Alt) plus latched variants whose PRIMARY cue is a rim drawn in the icon geometry — `GridStrokeThickness` is shared (`ActionIcons.cs:46`), so a thicker stroke would be a shared-control change; the filled margin dot stays secondary (the peripheral-vision rule, `ActionIcons.cs:23–27`, is why the dot cannot be primary). NOT an accent ring/fill on `DwellArcButton`: the dwell-progress arc is already `BrushAccent` (`DwellArcButton.cs:167`).
   - **Ring dim render (round-3 F2; round-4 F5):** `ActionMenuItemViewModel` gains an immutable `bool IsDisabled` set by `BuildLayer`. The render is a **per-button child-canvas group opacity**: `DwellArcButton.AddTo(Canvas)` accepts ANY canvas (`DwellArcButton.cs:362`) and places its parts with `Canvas.SetLeft/Top` relative to that parent (`:183–194`), so `ActionMenuWindow` adds a dimmed button into its own child canvas and sets `Opacity` on the canvas — true group opacity, still zero shared-control changes. Per-part opacity is REJECTED: stacked layers show through (RimHalo under Background, IconFill under IconStroke), and a hand-enumerated part list is the documented `GlassBackdropWindow.ClearButton` hazard (`:379–390`). Required test: a dim-state contrast test in the `HaloContrastTests`/`DwellProgressContrastTests` pattern — composite the dimmed button over worst-case backdrops (glass backdrop on/off, near-black and near-white desktop) and assert dimmed-icon vs dimmed-fill at or above an identifiability floor, dimmed separable from live, silhouette survives. The dwell-blend rule is moot by construction — a dimmed item has no target, so `ProgressPath` stays empty; pin that instead. A crossing re-runs the screen capture (`ScreenCaptureDelayMs` = 100, `ActionMenuWindow.xaml.cs:22`) — the Help toggle and More already pay that cost; acceptable, not hidden.

10. **Capture hygiene (round-1 F14):** `EdgeButtonBarWindow`'s constructor sets `ExcludeFromScreenCapture = true` (compare `ActionMenuWindow.xaml.cs:53`; the property is init-only but settable from a derived constructor). The exposure is real on the manual-selection path, where the capture centers on the unclamped `ManualSelectionCenter` (`ActionMenuWindow.xaml.cs:81–84`); one line fixes both bars.

## Pause interplay

The mod bar inherits `EdgeButtonBarViewModel.DwellActiveWhilePaused => true` (release-affordance semantics; round-4 audit: paused samples pass `SampleMayDwell` on this bar, but a menu cannot be open while paused, gap samples do not clear the gate — conservative — and no hole exists). The latch resets on show and ignores toggles while hidden, and the bar's gaze-sample override mirrors the base `Receive` order (`DwellOverlayViewModelBase.cs:97–102`: set `LastSampleWasPaused` from the message, check `IsVisible`, gate on `SampleMayDwell`, then the re-arm check) before any detector update. Latch toggling itself is OS-input-free.
