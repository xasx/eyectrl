# Dwell-Completion Audio Cue — Design

- **Date:** 2026-09-23 (rev 2, 2026-09-24 — external review round 1 applied: 13 findings, all verified against source)
- **Status:** Approved (owner, interactive session 2026-09-23); review round 1 findings applied — re-review pending
- **Branch:** `feat/dwell-audio-cue` (worktree `.worktrees/dwell-audio-cue`, base `c9225e2c`)
- **Origin:** competitive-feature queue re-rank 2026-09-22 (`docs/COMPETITIVE_FEATURE_ANALYSIS.md` follow-up tier, "dwell-completion audio cue — small, direct confirmation value for a gaze-only typist"); picked by owner as next queue item after #157 merged (PR #165).

## Problem

The only *interaction* sound in the app is the keyboard key click (`Assets/click.wav`, played by `KeyboardSoundService` from `KeyboardWindow.OnKeyDwellCompleted`, gated by `KeyboardSettings.ClickSoundEnabled`, default `true`). Every dwell outside the keyboard keys completes silently. (The one other sound in the app is the caregiver alert chime, `SystemSounds.Exclamation` at `CaregiverAlertWindow.xaml.cs:52` — an alert-onset safety signal, not interaction feedback.) For a gaze-only user a completed dwell is the primary "I did something" moment, and on surfaces where the visual effect is subtle or delayed (toolbar toggles, task-switcher switches, settings rows) there is no immediate confirmation channel. Hearing the activation closes that feedback gap without requiring a visual check.

## Behavior

A short, soft confirmation tone plays when a dwell **activates** (completes), split into two sound families:

| Family | Surfaces | Sound | Gate |
|---|---|---|---|
| Typing (existing) | Keyboard keys; prediction-bar accepts (new); emoji picks (already routed as keys) | existing `click.wav` | `KeyboardSettings.ClickSoundEnabled` (default **true**, unchanged) |
| Cue (new) | Toolbar band, action-menu ring, modes menu, quick-actions grid, task switcher, right-edge bar, activation button, glass-backdrop hide, drag targets, settings (Tab/Control/Pagination/Modal), emoji category bar, eye-care banner, notes overlay, manual-selection dwells | new `Assets/dwell-cue.wav` (~50 ms soft tone) | new `DwellSettings.CueEnabled` (default **false**, owner choice) |

**Deliberately excluded:** external-app dwells (`ExternalDwellService` — owner declined), repeat-mode re-fire ticks (timer-driven in `RepeatModeController`, not dwell completions), `ScrollOverlayViewModel` and `ManualSelectionOverlayViewModel` (their `OnTargetActivated` overrides are empty — no effect to confirm; they opt out of publishing, see Mechanism), Supervisor UI (out of scope), and Core (framework-agnostic — no sound concerns there).

**Volume note:** the activation button and the action ring are both cue surfaces, so one ordinary two-step click produces two tones under the enabled toggle. That is acceptable behind a default-off toggle; per-surface curation is the recorded escape hatch (Out of scope).

## Mechanism

Approved approach: **activation message + single subscriber** (alternatives in ledger D7). Two invariants govern every publish site:

- **Boundary rule** — publish where the **detector event arrives**, never inside dispatch methods that non-dwell paths (mouse-click fallback, `SimulateActivated`, test hooks) also call.
- **Post-effect rule (D8)** — publish **after** the surface's effect has actually run, never before. This makes the toggle self-demonstrating (dwelling the toggle ON plays the cue as confirmation because `CueEnabled` is already `true` by then; dwelling it OFF is silent), and it makes a throwing sound path structurally incapable of cancelling the user's activation.

1. **Message** — new empty record `DwellActivationMessage` in `EyeCtrl.ViewModels/Messages/InteractionMessages.cs`. Published on the UI thread (gaze messages reach every base-class VM on the UI thread, `GazeEngineAdapter.cs:156,167`). Empty payload by design (D5).
2. **`DwellOverlayViewModelBase`** (`src/EyeCtrl.ViewModels/DwellOverlayViewModelBase.cs`) — the base class currently subscribes `DwellDetector.TargetActivated += OnTargetActivated` (line 29). It will instead subscribe a private wrapper `OnDetectorTargetActivated` that (a) calls the existing virtual `OnTargetActivated(targetId)` (the effect) first, then (b) publishes `DwellActivationMessage` when the new protected virtual property `AnnounceDwellActivation` is `true` (default). This covers all nine effectful derived VMs — Toolbar, ActionMenu, ModesMenu, QuickActionsGrid, TaskSwitcher, EdgeButtonBar, ActivationButton, GlassBackdrop, DragTrail — with **zero derived-constructor changes** (the "zero ctor changes" claim is scoped to derived VMs only; two App-side stragglers do take a new optional parameter, see below). The two empty-handler VMs (`ScrollOverlayViewModel`, `ManualSelectionOverlayViewModel`) override `AnnounceDwellActivation => false`. **`OnDispose` must detach the wrapper by name** (`TargetActivated -= OnDetectorTargetActivated`) — the existing `-= OnTargetActivated` at line 89 becomes a silent no-op after this change. The wrapper sits on the detector subscription, so the derived VMs' `Simulate*`/`ActivateForTest` direct calls into `OnTargetActivated` stay silent (they bypass the detector event).
3. **Stragglers with their own detectors/dispatch** publish where the detector event arrives, after their effect:
   - `SettingsWindowViewModel` — the four detector-subscription lambdas (`src/EyeCtrl.ViewModels/SettingsWindowViewModel.cs:89–98`: `_tabDwell`/`_controlDwell`/`_pagDwell`/`_modalDwell`), each becoming `id => { OnTargetActivated(id, cat); Messenger.Send(DwellActivation); }` — covering all four categories including modal Yes/No. NOT inside the private `OnTargetActivated(id, category)` dispatch (line 187): `SimulateActivated` (line 178, mouse-click fallback and tests) routes through it too, and a mouse click is not a dwell completion.
   - `EmojiGridManager.OnCategoryDwelled` (`src/EyeCtrl.App/Overlays/EmojiGridManager.cs:97`) — publish at the end of the handler; category switching is navigation, not text insertion (D1). **The class has no messenger** (ctor takes visuals + callbacks + optional sink/registry): add an optional trailing ctor parameter `IMessenger? messenger = null` resolving to `WeakReferenceMessenger.Default` (D9) — which is byte-identical to the app's registered instance (`services.AddSingleton<IMessenger>(WeakReferenceMessenger.Default)`, `AppBootstrapper.cs:82`), so the fallback sends on the real bus while tests inject a fake.
   - `EyeCareBannerWindow` (`src/EyeCtrl.App/Overlays/EyeCareBannerWindow.xaml.cs:103`) — same treatment: optional trailing `IMessenger? messenger = null` (ctor currently `(int dwellMs, IStruggleTelemetrySink?, IDwellDetectorRegistry?)`), publish at the end of `OnTargetActivated` (`Resolve(...)` is the effect).
   - `NoteManager.OnTargetActivated` (`src/EyeCtrl.App/Services/NoteManager.cs:260`) — already takes an `IMessenger`; publish at the end of the handler, after the note action.
   - `ManualSelectionDwellService.OnDwellActivated` (`src/EyeCtrl.App/Services/ManualSelectionDwellService.cs:358`) — publish **inside the `DispatchSafe` continuation, after the `_dwellDetector == null` bail-out** (`:364–368`: the session may have ended between the detector event and the dispatched continuation; completing into a torn-down session must not cue either), next to / after the `ManualSelectionDwellCompletedMessage` send (`:378`). Already takes an `IMessenger`.
   - The **prediction bar** does NOT publish the cue message: `KeyboardWindow.OnPredictionDwelled` (`KeyboardWindow.xaml.cs:745`) calls `_soundService?.PlayKeyClick()` **inside the guard block** (after the `pred_` prefix check and the rendered-index range check — a stale index resolving to a no-op must not click), alongside `HandlePredictionSelected`. Prediction accepts are typing (D1). Emoji cell picks already flow through `OnKeyDwellCompleted` as keys.

4. **`DwellCueService`** (`src/EyeCtrl.App/DwellCueService.cs`, new) — primary ctor `(DwellSettings settings, string wavPath, Func<string, SoundPlayer?>? playerFactory = null)`; the factory is the test seam, defaulting to real `SoundPlayer` construction.
   - **Robustness (lesson from review #3):** `File.Exists` alone does not make `Play()` safe — a corrupt wav, or a file deleted/quarantined after startup, passes an existence check and `SoundPlayer.Play()` validates on the calling thread and throws. Since `WeakReferenceMessenger.Send` runs handlers synchronously, an unguarded throw would previously have cancelled the activation itself; the post-effect rule now makes that impossible, and the service additionally (a) preloads with `player?.Load()` inside a try/catch in the ctor (a corrupt file ends as a null player — genuinely silent no-op), and (b) wraps the `Play()` call in try/catch inside the handler (precedent: `CaregiverAlertWindow.xaml.cs:50–57`), logging at most once per occurrence.
   - Handler: `if (settings.CueEnabled) try { player?.Play(); } catch { log }`. Reads the **live** settings object, so toggling applies without restart (same as `ClickSoundEnabled`).
   - **Registration (lesson from review #2):** DI singletons are lazy (`AppBootstrapper.cs:296`), and nothing depends on `DwellCueService` — a bare registration would never construct, never subscribe, never play, and every unit test would still pass because tests construct it directly. Registration is therefore a **factory lambda** (`sp => new DwellCueService(sp.GetRequiredService<EyeCtrlSettings>().Dwell, Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "Assets", "dwell-cue.wav"))` — the same `GetRequiredService<EyeCtrlSettings>()` factory shape the bootstrapper already uses at `:286–327`), plus an **eager discard-resolve** in `App.xaml.cs` next to `DwellTimeRouter` (`App.xaml.cs:197`, with the same "must exist before surfaces register" comment style). The messenger-subscribing precedent is `ManualSelectionDwellService` (ctor-subscribes, discard-resolved at `App.xaml.cs:192`), not `DwellTimeRouter` (which subscribes provider events, not `IMessenger`).
5. **Asset** — `Assets/dwell-cue.wav`: **generated by a committed script** `tools/gen_dwell_cue.py` (the `tools/gen_dicts.py` precedent) with pinned parameters recorded there and here: 16-bit PCM, 44.1 kHz, ~50 ms, sine (~880 Hz) with fast exponential decay, peak ≤ −20 dBFS. Committed as binary; `<Content Include>` + `<ExcludeFromSingleFile>true</ExcludeFromSingleFile>` exactly like `click.wav` (`EyeCtrl.App.csproj:51`). Amplitude IS the volume — `SoundPlayer` exposes no volume control (D4). A float32 export would be rejected by `SoundPlayer`; the format is pinned and tested (Testing).

- Row on the Dwell tab: `ToggleSpec("d_cue_sound", "Dwell Completion Sound", …)` in `DwellPageSource`, getter/setter + `ApplyAndSave()` like siblings. The descriptions-completeness gate binds it automatically (every row needs a description — one is written).
- `d_reset` ("Reset Dwell Settings") learns `d.CueEnabled = def.CueEnabled;`.
- **Drift guard must be generalized (lesson from review #1):** `KeyboardPageSourceResetDriftTests` enumerates `new KeyboardPageSource(ctx).Build()` only (`KeyboardPageSourceResetDriftTests.cs:54,84`) — it cannot see a Dwell page row, and the only `d_reset` test today samples one field (`SettingsPageSourceCallbackTests.cs:104`). Leaving `d.CueEnabled` out of `d_reset` would keep the suite green — the #157 bug class on the next page over. The guard's enumerate-perturb-assert machinery is extracted so every page source with a `*_reset` button can use it; **Keyboard and Dwell are covered now**. `GeneralPageSource` (which has `g_reset`, `:34`) is **deliberately excluded pending issue #164** — its `g_theme`/`g_track` gap is an open owner curation decision, and including it would turn an open question into a permanently red suite (ledger D10). Teeth are proven the #157 way: delete the new reset line and watch the guard fail, then restore.
- #153 per-setting tolerance in `SettingsService.Load` covers a plain bool automatically (a bad value drops through the section drop-one retry, `SettingsService.cs:293–299`). No new tolerance test; the plan spot-verifies a hand-edited `"cueEnabled": "bogus"` degrades to default without wiping the section.
- **Not** added to `KeyboardStackSnapshot` (`SettingsSnapshots.cs`): that record captures "every input the prediction stack is rebuilt from" (`SettingsSnapshots.cs:26`) — `CueEnabled` is not one; adding it would trigger pointless prediction-stack rebuilds.

## Pause interplay

The cue means "a dwell completed — and something happened", not "the OS effect fired" (D2). Surfaces that did not opt into `DwellActiveWhilePaused` cannot activate while paused at all (`SampleMayDwell` gate). Opt-in surfaces (task switcher tiles, quick actions) suppress only the OS-input effect via `LastSampleWasPaused` and still perform their own dismissal — an activation always *does* something visible, so the sound is truthful in every reachable state. **Direct sites:** the settings window's `Receive` (`SettingsWindowViewModel.cs:105–124`) has no pause gate — settings dwells run while paused, and the cue is truthful there too (the activation switched a tab or applied a setting). The post-effect rule is what keeps this honest everywhere: the cue only ever fires for an activation whose effect actually ran, including the ManualSelection torn-down-session bail-out (no effect ⇒ no cue).

## Error handling

- Missing/unreadable wav ⇒ null player ⇒ no-op. Corrupt-but-present wav ⇒ caught at `Load()` in the ctor ⇒ null player. Deleted-after-startup ⇒ caught at `Play()` ⇒ logged, swallowed. No path from a sound failure to a lost activation (post-effect rule + try/catch).
- Each `SoundPlayer.Play()` **cuts off** the previous in-process sound (winmm `PlaySound` semantics — they do not overlap). Harmless at ~50 ms for repeated cues; note that cue and key-click also cut each other, which at these durations is imperceptible.
- **Caregiver-chime interplay (verification item, review #9):** `SoundPlayer.Play()` is winmm `PlaySound` without `SND_NOSTOP`; whether it truncates a concurrently playing `SystemSounds.Exclamation` (MessageBeep-backed) is not verifiable headless. Live check during the owner-gated verification launch: play the chime, then cue ~50 ms later, and listen. If truncation is real, suppress the cue while `CaregiverAlertWindow` is showing (decision then; not pre-built — the chime currently fires only with adaptation alerting enabled).
- Service is a DI singleton subscribed for the process lifetime (`ManualSelectionDwellService` precedent) — no unsubscription path needed, no leak.

## Testing strategy

- **ViewModels.Tests** — base class: a minimal test subclass of `DwellOverlayViewModelBase` publishes `DwellActivationMessage` after the effect runs (drive the `DwellDetector` via `Receive`/`GazeCursorMovedMessage` samples; assert effect-then-publish ORDER); an `AnnounceDwellActivation = false` subclass publishes nothing; disposing the VM stops publishing (pins the `OnDispose` wrapper detach, review #13). `SettingsWindowViewModel`: a real detector activation publishes; `SimulateActivated` does NOT (pins the boundary rule against mouse fallbacks); the toggle row's own Set → publish order demonstrates the self-demonstrating toggle (ON cues, OFF silent). Real-subclass coverage (repo trap: synthetic-subclass tests can't prove real-subclass wiring): a reflection test over the `EyeCtrl.ViewModels` assembly pins the opt-out set to exactly `{ScrollOverlayViewModel, ManualSelectionOverlayViewModel}` — default is `true`, so a future effectful VM is covered with no action; the pin forces any new opt-out to be a conscious decision that touches the test.
- **App.Tests, service** — unit tests with the player-factory seam (recording fake): enabled + message ⇒ `Play()` recorded; disabled ⇒ not; corrupt wav content on disk ⇒ null player, no throw; `Play()` throwing ⇒ swallowed, no propagation (post-effect rule independently proven by the VM order test). **Wiring test** (review #2): build the real container the way `AppBootstrapper` registers it, resolve `DwellCueService` (proves registration + constructibility), send `DwellActivationMessage`, assert the handler ran (observable via the seam the plan chooses — e.g. internal last-handled stamp; the real wav is NOT played in tests). Precedent for building the real provider: `DwellRoutingRegistrationWiringTests`.
- **App.Tests, per-site publish tests (review #10)** — one per direct site, each mutating cleanly to prove teeth: `EmojiGridManager` (existing emoji-dwell test infra builds it, `KeyboardEmojiDwellFeedbackTests`), `EyeCareBannerWindow` (`[StaFact]`), `NoteManager` (injected messenger), `ManualSelectionDwellService` (injected messenger; includes the torn-down-session case publishing NOTHING — the bail-out is before the publish). Deleting any publish keeps a red test.
- **Census allowlist (review #11)** — a headless drift test over every `new DwellDetector(` / `TargetActivated +=` site in `src/` (seven files outside the base today: EmojiGridManager, KeyboardWindow prediction, ExternalDwellService, EyeCareBannerWindow, NoteManager, ManualSelectionDwellService, SettingsWindowViewModel), each classified **cue / typing / excluded** with the classification's reason, plus a staleness check in the `ToolbarButtonDriftTests` `ReachableElsewhere` pattern — a new surface with its own detector cannot ship silent and unnoticed.
- **Asset (review #12)** — headless test parses the committed `dwell-cue.wav` RIFF header: PCM 16-bit, 44.1 kHz, duration ≈ 50 ms, peak ≤ the pinned level, and `new SoundPlayer(path).Load()` accepts it. The generator script itself is committed (`tools/gen_dwell_cue.py`) so the asset is reproducible.
- **Drift guard** — the generalized guard covers the new `d_cue_sound` row (Keyboard + Dwell); teeth proven by the delete-the-reset-line mutation (review #1).
- Full gates before handoff: Core, ViewModels, App (non-UI + gated UI where applicable) green; GitNexus `impact` before edits (`DwellOverlayViewModelBase` upstream — expect the 11-VM fan, LOW risk: additive publish) and `detect_changes` before commit.

## Out of scope / future work

- Cue for external-app dwells (`ExternalDwellService`) — owner declined for now; would be one more publish site if wanted.
- Per-surface cue curation (e.g., cue everywhere except the activation button / ring to avoid the two-tone ordinary click) — single toggle only; split later if the owner finds a surface noisy.
- Cue volume / additional sounds (two-tier feedback) — declined in brainstorm (YAGNI).
- Caregiver-chime truncation suppression — pending the live verification item in Error handling.
