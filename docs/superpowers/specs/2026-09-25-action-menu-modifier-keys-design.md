## Problem

Every mouse action EyeCtrl simulates is bare. `IInputSimulator`'s click and wheel methods carry no modifier state, the ring's `InteractionAction` has no modifier dimension, and a gaze-only user therefore cannot perform any of the ordinary held-modifier gestures a physical-mouse user does without thinking: Shift+click (range select), Ctrl+click (multi-select, open-in-new-tab), Alt+click (per-app semantics), Ctrl+wheel (browser zoom, Explorer icon scale). The keyboard half of this already exists — `ModifierKey` (`src/EyeCtrl.Core/Keyboard/ModifierKey.cs`), the keyboard's latched modifiers (`KeyboardViewModel.cs:68` field, `:70` copy-on-read property), atomic modified key sequences (`Win32InputSimulator.BuildModifiedKeySequence`) — but nothing connects it to the mouse path, and no UI offers a mouse modifier while the action menu is open.

Display and owner context: 3840×2400 physical at 200% = **1920×1200 DIP** (probed). Owner settings (read-only): `viewPosition: atCenter`, **`selectionMode: manualSelection`** (menu opens via the manual path: activation dwell → zoom view → precise dwell → menu), `keySizeMultiplier: 1.5`, toolbar Top-docked, `adaptation.enabled: false`. Margin arithmetic: `GeometryMaxMarginPx` is a **0–300 user setting** (`AdaptationSettings.cs:83–84`); the effective margin is fraction × base clamped to it (`GeometryRouter.cs:55–56`); the owner's `geometryBiggerMaxFraction` 0.5 binds first — mod buttons ≤ 50 px, ring items ≤ 70 px; fractions cap at 1.0, so the mod bar's absolute worst case is 100 px. The owner's rings are SIX slots on both layers (manual path adds Back); the six-slot neighbour GAP is 115 DIP (the chord is 255 DIP — `ActionMenuSettings.cs:35–36`). Ring geometry: effectiveRingRadius 255 DIP, menu-center clamp 325 DIP (`ActionMenuLayoutHelper.cs:32–35`); edge-button centers inset 30 + 50 + 10 = 90 DIP from an edge, radius `UIConstants.ButtonRadius` = 50; mod-button centers 240 px physical apart, base radius 100 px.

## Behavior

While the action menu is open (normal and manual-selection path alike), the LEFT screen edge shows three dwell buttons — **Shift, Ctrl, Alt, top to bottom** — mirroring the right-edge Close/Help pair:

- Dwell a button → that modifier **latches** for the current menu session (visual latched state). Dwell it again → unlatches. Multiple modifiers can latch at once (Ctrl+Shift+click).
- **Re-arm rule (round-1 blocker fix; rounds 3–5 converged into one consolidated rule — mechanism 9):** after a toggle activation, the button cannot re-accumulate until the user has genuinely left it: while the re-arm is pending AND the pending button is the target the detector itself would select, gaze samples are fed to the detector as hitting-nothing; the pending clears only after gaze has stayed off the button's effective hit region for D = 150 ms of consecutive VALID samples (blink-gap samples restart that clock). Net contract: a mod button **toggles once per gaze entry**.
- **Refusal is structural (round-3 F3):** while the latch is non-empty, Drag and ScrollMode are **not dwell targets at all** — `BuildLayer` skips their `AddTarget` (slot angles preserved: the step still divides by the full item count), so their arcs never fill, no activation fires, no completion cue plays, and no `Activated` outcome reaches the struggle sink. The slot still renders, **dimmed** via a per-button child-canvas group opacity (mechanism 9) — a disabled control that does not pretend to work. The `OnTargetActivated` refusal branch stays as a defensive backstop only.
- Picking a ring action sends the latched set with the selection. The simulated input is **one atomic SendInput batch** per click: modifier key-down(s) → the mouse down/up event(s) → modifier key-up(s) in reverse. DoubleClick is ONE batch (mods↓, down, up, down, up, mods↑) — the exact event shape a physical user produces. When Alt is in the set, an unassigned menu-mask key (VK `0xE8`, the AutoHotkey `#MenuMaskKey` precedent) is injected down+up immediately before the Alt key-up. A modified wheel batch leads with a MOVE|ABSOLUTE event: wheel events alone land at the current cursor, and `ResetToFreeLook` re-enables the per-frame gaze `MoveCursor` across a doubly-deferred dispatch (`Win32InputSimulator.cs:85–87`, `GazeEngine.cs:597–601`).
- **Partial-send compensation (best-effort, stated honestly):** the send path observes the injected count; when 0 < sent < count, compensating events are sent — a mouse-up for each unmatched mouse-down (BEFORE the modifier ups), the mask pair before a compensating Alt-up, and key-ups for modifiers whose down landed AND whose up did not (including a landed-but-unmatched mask down). A fully blocked batch (UIPI, sent = 0) injects nothing and needs none. A compensation failure gets its OWN log line — `SendRaw`'s 30 s rate limit (`:295–296`) would otherwise suppress it milliseconds after the partial-send warning. The design goal is "a partial send cannot silently weld modifiers down", not an absolute guarantee.
- Applies to the click family (Left/Right/Middle/Double) and the one-shot scroll family (Up/Down/Left/Right). **Modified scrolls send ONE wheel notch** — the four arms map to (0,+1), (0,−1), (−1,0), (+1,0) with delta 1 when modified (ledger L9, with the owner-cost statement and its caveats below).
- **One-shot lifecycle:** the latch exists only for the current menu opening — reset on every show BEFORE `BuildLayer()` reads it for the dim state, cleared on hide, toggles ignored while the menu is hidden (the coordinator's hide is deferred twice, `OverlayMessageCoordinator.cs:158`, while the VM's reset runs synchronously). It survives More/BackToPrimary layer switches (`BuildLayer` re-reads the latch each rebuild — pinned by test).

**Known geometry limits (recorded; follow-ups, not v1 work):** under AtGaze a ring item can overlap the mod buttons — center-to-center distances of ~7.5–42 DIP mean the circles overlap by up to ~80 DIP against radii 70 + 50; the shipped right bar has the same defect today. A menu opened over a visible keyboard puts the lower mod button near the keyboard's bottom-left keys — reachable for this owner (bottom-docked keyboard at the 75%-height anchor, 1.5× keys) INDEPENDENT of ViewPosition. A LEFT-docked toolbar (`ToolbarSettings.DockedEdge` supports Left, 120-DIP band) would sit directly under the mod bar; the owner docks Top. All three belong to one geometry pass (see Geometry limits). Within the ring: neighbour capture of a dimmed slot's drawn disc requires the margin to exceed the neighbour GAP (chord − 140 DIP): 230 px physical at the owner's six slots — impossible (the ring margin is fraction-capped at ≤ 140 px); reachable on a nine-slot layer at > 69 px physical, which the owner's current 70 px bound just exceeds (round-4 F6, stated with the bound).

## Mechanism

1. **Core — pass-through only** (`src/EyeCtrl.Core/Processing/InteractionManager.cs`): `OnActionSelected(InteractionAction action, IReadOnlySet<ModifierKey>? modifiers = null)`; the `ActionRequested` event gains the same trailing parameter. Core stores nothing and branches on nothing. BOTH raise sites pass it: the action-menu path (`:224`) forwards the parameter; the repeat-mode tick (`:362`) passes `null` (Core test pins that repeat ticks carry no modifiers). Production blast radius: one caller (`GazeEngineAdapter.cs:107`), one subscriber (`GazeEngineAdapter.cs:63`); the 15 test-subscriber lambdas across 6 files gain the third parameter (census verified exact by round 1).

2. **Messages** (`src/EyeCtrl.ViewModels/Messages/InteractionMessages.cs`): `ActionSelectedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`; new `ToggleActionMenuModifierMessage(ModifierKey Modifier)`; `ActionRequestedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`.

3. **The latch lives in `ActionMenuViewModel`**, mirroring the keyboard's precedent:
   - `Receive(ToggleActionMenuModifierMessage)` toggles and raises — **only when `IsVisible`**; a toggle deferred past a hide lands on a closed menu and is dropped.
   - `Receive(ShowActionMenuMessage)` resets the latch **before** `BuildLayer()` (which reads it for the dim state); `Receive(HideActionMenuMessage)` clears it.
   - **Capture means COPY:** `OnTargetActivated` snapshots `new HashSet<ModifierKey>(backing)` into the `ActionSelectedMessage` (the `KeyboardViewModel.cs:70` copy-on-read precedent). The hide is queued ahead of the action message (`InteractionManager.cs:213` vs `GazeEngineAdapter.cs:279–280`/`:334`), so an aliased set really would arrive empty.
   - **Dimmed = not a target:** `BuildLayer` computes every slot's position (angle step over the FULL item count, so geometry never shifts) but skips `DwellDetector.AddTarget` for items whose action is Drag/ScrollMode while the latch is non-empty; each item VM carries an immutable `IsDisabled` flag for the render. On a latch empty↔non-empty crossing the VM calls `BuildLayer()` (which re-reads the latch and bumps `RingVersion` LAST, per the pinned ordering at `:151`) — the coordinator's existing `RingVersion` branch then redraws from the freshly rebuilt `Items`; a bare `RingVersion++` would redraw stale items and never dim (round-3 F2).
   - **Backstop refusal:** `OnTargetActivated` for Drag/ScrollMode with a non-empty latch sends nothing and returns — unreachable while dimmed items have no target, kept as a guard against ordering surprises.

4. **Input layer** (`src/EyeCtrl.Core/Interfaces/IInputSimulator.cs`, `src/EyeCtrl.Platform/Input/Win32InputSimulator.cs`):
   - New default-interface-method overloads `LeftClick/RightClick/MiddleClick/DoubleClick(PhysicalPoint, IReadOnlySet<ModifierKey>?)` and `Scroll(PhysicalPoint, int, int, IReadOnlySet<ModifierKey>?)`, default bodies throwing `NotSupportedException` (the `MiddleClick` precedent, `IInputSimulator.cs:30`) — existing fakes compile; a fake that actually receives a modified call fails loudly.
   - **Pure seam, characterization scoped to the real gap:** the wrapping is a new internal static pure builder `WrapWithModifiers(IReadOnlySet<ModifierKey>?, INPUT[] body)` — downs in `BuildModifiedKeySequence`'s order (Ctrl, Alt, Win, Shift; only Shift/Ctrl/Alt arrive), body, ups reversed, plus the Alt mask pair. Two `BuildModifiedKeySequence` tests exist (`Win32InputSimulatorClampTests.cs:37` no-modifier shape, `:49` Ctrl+Shift order/reversed-ups); characterization extends coverage to **Alt, the Win extended flag, and extended main keys** BEFORE the extraction.
   - `SendRaw` gains an `int` return (the injected count; it remains the per-frame `MoveCursor` path — a return value costs nothing there). The new mouse overloads compose `WrapWithModifiers` output and send through `SendRaw`; on `0 < sent < count` the Behavior-paragraph compensation is issued, and a compensation send failure is logged on its OWN line, not through the rate-limited path. `SendModifiedKeyPress` (direct `NativeMethods.SendInput` today, `:155`) adopts the same `SendRaw` + compensation path — **this changes the shipped keyboard send path, so Task 1 carries keyboard regression coverage**.
   - `DoubleClick(pt, mods)` = ONE batch (down, up, down, up between the modifier pair). Null/empty modifiers ⇒ exactly the current byte stream — including `Scroll`'s two separate `SendInput` calls for the X/Y legs (`:84–95`) and the unmodified wheel's lack of a leading MOVE (pre-existing; follow-up 4).

5. **Dispatch** (`src/EyeCtrl.App/Services/Coordinators/KeyboardInteractionDispatcher.cs:143`): explicit routing — `mods is { Count: > 0 } ? simulator.X(pt, mods) : simulator.X(pt)`; the four scroll arms map to (0,+1), (0,−1), (−1,0), (+1,0), each with delta 1 on the modified arm (`DefaultScrollAmount = 3` stays unmodified). Never a blind nullable pass: with null it must behave byte-identically AND `TestFakes.FakeInputSimulator` (`TestFakes.cs:342`) does not implement the overloads. Throwing defaults catch stray calls; only recorded-modifier assertions catch dropped ones (Testing). The `Log.Information` line gains `Modifiers={Modifiers}`.

6. **Left-edge bar — second instance, not a subclass** (`EdgeButtonBarWindow`/`EdgeButtonBarViewModel` reused): the dwell registry is owner-keyed (`DwellDetectorRegistry.Register(object owner, …)`); both routers iterate the registration snapshot without keying by context (`DwellTimeRouter.cs:38`, `GeometryRouter.cs:49`). **DI shape:** the existing unkeyed `AddSingleton<EdgeButtonBarViewModel>()` (`AppBootstrapper.cs:381`, resolved at `:637`) stays as the right bar; exactly ONE keyed singleton is added for the mod bar. `IOverlayManager` gains `IEdgeButtonBar ActionMenuModBar` as a **default interface property whose default throws** — the six fakes keep compiling, and `TestFakes.PartialOverlayManager` (`TestFakes.cs:277`) gains an OPTIONAL mod-bar slot so `HideActionMenuBarOwnershipTests` (built via `MakeOverlayManager`, `:164–168`) can exercise the new paths. The positional `OverlayViewModels` record gains the member at both construction sites (`App.xaml.cs:198`, `AppBootstrapper.cs:627`) and the `ResolveViewModels` tuple (`App.xaml.cs:572–595`); `OverlayManager` builds/binds/wires a second `EdgeButtonBarWindow` exactly like the first (`:112`, `:138–154`).

7. **Definitions** (`src/EyeCtrl.App/Services/ActionMenuModifierButtons.cs`, new): three `EdgeButtonDefinition`s — ids `ActionMenu_mod_Shift` / `ActionMenu_mod_Ctrl` / `ActionMenu_mod_Alt`; `Activate` sends `ToggleActionMenuModifierMessage`; `RadiusLogical = UIConstants.ButtonRadius` (`UIConstants.cs:18`, NOT the ring's `ActionMenuButtonRadius`); labels always shown; dwell = the menu's ring dwell (`ShowBack ? ManualSelectionActionMenuDwellMs : ActionMenuDwellMs`); VerticalOffsets `0, ±(2·ButtonRadius + ManualSelectionSideButtonGap)` (`UIConstants.cs:37`), logical px converted with `DpiHelper.LogicalToPhysicalY` exactly like `ActionMenuEdgeButtons.cs:30–31` (`AddTarget` adds the offset to the anchor in physical space, `EdgeButtonBarViewModel.cs:107`). The definitions FACTORY (latched/unlatched variants per current latch) is shared between the show path and the rebuild path; only the anchor and the `ShowButtons` call are show-path-only.

8. **Show/hide placement (round-2 Finding 2 — fault isolation):** both handlers run inside ONE shared try/catch today (`OverlayMessageCoordinator.cs:116–153`, `:160–189`); a mod-bar fault must not kill the right-bar hide (the strongest safety net in the app — a gaze-only user holding a pressed mouse button with nothing on screen to release it). Therefore: each bar gets its OWN try block, and in BOTH handlers the left bar is handled AFTER the right bar. Show: right-bar `ShowButtons` first (`:131–138`), then the left-bar show — still BEFORE the `ResolvedControl == null` early return at `:140`. Hide: the right-bar ownership-guarded hide first, then the left-bar hide — unconditional (nothing else ever owns the left bar), outside the ownership `if`, inside its own try. Its body: `ReplaceButton` for the ONE toggled id, reached via the bar's `EdgeBarVm` (`IEdgeButtonBar.cs:40` — no new interface member; both implementers stay untouched). A latch empty↔non-empty crossing instead routes through the VM's `BuildLayer()` for the ring dim (mechanism 3); the bar icons still swap via the coordinator branch.

   - **The consolidated re-arm rule (round-5 convergence — replaces the round-3/4 gate bullets entirely):**
     - **State:** `string? _pendingId` and `long? _exitStartUs` — at most ONE pending, ever. It is set to the activating id BEFORE `def.Activate(Messenger)` runs; setting it **supersedes any other pending and starts a fresh exit clock** (round-5 F2: two pendings DO coexist in production at margin > 20 px — the lens where Ctrl is nearest-hitting but inside Shift's enlarged region lets Ctrl complete while Shift's exit clock never runs, and per-id pendings then leave Shift gated-dead until the user happens to spend 150 ms outside Shift's grown circle; supersede removes that case, and is safe because clearing a superseded id would have required a 600 ms nearest-hitting dwell on the other button). Cleared by `ShowButtons`, `Hide`, and `RemoveButton(id)` when the id matches.
     - **Core selection extraction (round-5 F3):** `DwellDetector.cs:325–345` is refactored into `public string? NearestHittingTargetId(PhysicalPoint, Func<DwellTarget,bool>? filter = null)`, which `Update` itself calls — the VM reads the detector's OWN selection instead of duplicating it. The duplicate could drift three ways: tie-break order (`_targets` is a `ConcurrentDictionary` — hash-order snapshots with a strict `<` first-wins — vs a VM `Dictionary`'s insertion order, hit by integer-midpoint test points), any future detector-selection change, and a missed map-maintenance site. The SAME extraction provides the exit clock's inside-test as an id-keyed region read on the detector (e.g. `bool TargetHit(string id, PhysicalPoint)` beside `GetProgress`, `:431+`): the gate asks "would the detector select the pending target", the clock asks "is gaze inside the pending target's current effective region" — and neither reads a VM-retained instance, keeping round-5 F9's staleness dead (the detector stores instances by reference; the router's geometry maps mutate them, `DwellTarget.cs:89`; `DwellDetector.cs:109–116`). Lands in Task 2 (or the start of 4a) with Core tests; it deletes the VM instance map, the retained-instance read, and the per-sample resolution machinery from rev 4/5. The refactor must keep `Update`'s behaviour byte-identical — the existing detector suite plus a tie-break test pin it (the tie winner is whatever the detector's own order produces; the API must agree with `Update`, not pick its own).

       2. `!SampleMayDwell` ⇒ return.
       3. ## Pause interplay

The mod bar inherits `EdgeButtonBarViewModel.DwellActiveWhilePaused => true` (release-affordance semantics). A paused session cannot have an open menu (`TogglePause` hides it, `InteractionManager.cs:284`), the latch resets on show and ignores toggles while hidden, and the bar's gaze-sample override mirrors the base `Receive` order (`IsVisible` → `SampleMayDwell` → re-arm check → update) without touching `LastSampleWasPaused` (private setter — the Toolbar/DragTrail override pattern). Latch toggling itself is OS-input-free.
