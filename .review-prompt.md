## What to verify (cite spec sections + file:line for each finding)

1. **Fidelity to the codebase.** Every claim about existing code must match reality. Read these to check the spec's seams:
   - `src/EyeCtrl.Core/Models/InteractionAction.cs` — the enum the spec extends
   - `src/EyeCtrl.Core/Processing/InteractionManager.cs:130-169` — `OnActionSelected`, the target-point resolution + state-machine special-cases (ScrollMode at :146, Drag at :160)
   - `src/EyeCtrl.App/Services/EventCoordinator.cs:1370-1408` — `HandleActionRequested`, the IInputSimulator dispatch switch at :1391
   - `src/EyeCtrl.Core/Settings/ActionMenuSettings.cs` — default `VisibleActions` + `EnsureDefaults`
   - `src/EyeCtrl.Platform/Services/Win32WindowManager.cs` + `src/EyeCtrl.Core/Interfaces/IWindowManager.cs` — where the new resolver/ops land
   - `src/EyeCtrl.Platform/Services/ControlFinder.cs` — the spec claims it only resolves leaf controls and never walks to a containing Window; confirm
   - `src/EyeCtrl.ViewModels/ActionMenuViewModel.cs` + `Messages/InteractionMessages.cs` — `BackSelectedMessage`, `ShowActionMenuMessage`, `ActionSelectedMessage`
   Flag any seam the spec names that doesn't exist, or any dispatch site over `InteractionAction` the spec **misses** (grep the whole `src/` tree — a missed switch case is the classic enum-extension bug).

2. **API surface fit.** The spec adds `TopLevelWindowFromPoint` + `Minimize/Maximize/Restore/Close` to `IWindowManager`. Is that the right interface, or does it belong on `IInputSimulator` (mouse/keyboard) / a new abstraction? Judge by how `Win32WindowManager` is already consumed (Task Switcher) and whether window *operations* belong next to window *enumeration*.

3. **Win32 correctness.** Spec picks `PostMessage(WM_CLOSE)` for Close (graceful) and `ShowWindow(SW_MINIMIZE/SW_MAXIMIZE/SW_RESTORE)` for the rest, with `IsZoomed` driving the Maximize/Restore toggle and `GetAncestor(GA_ROOT)` to find the top-level HWND from a child. Are these the right choices vs. alternatives (`WM_SYSCOMMAND SC_*`, `TerminateProcess`, `GetParent` loop)? Flag any case where the chosen call silently does the wrong thing (UWP, fullscreen, already-minimized, console-host, owned windows).

4. **Edge cases & safety.** Does the spec's §6 cover: target = desktop (no window), target = EyeCtrl's own overlay, target = a child/owned window, Close on unsaved work, Maximize/Restore on a fullscreen (F11) window, multi-monitor points (still primary-only per gap #7)? Are any safety-critical cases missing — e.g. closing the foreground window the action menu was invoked from, or the resolved HWND going stale between menu-open and action-fire?

5. **UX / dwell implications.** The spec adds a "Window" sub-menu via a new `ShowWindowMenuMessage` that re-shows the *same* `ActionMenuWindow` with a filtered list. Is this consistent with how `ActionMenuWindow` is shown today (via `ShowActionMenuMessage`)? Will the existing dwell machinery (per-surface dwell times, `DwellOverlayViewModelBase`, the Back button) work unchanged for a second-level menu, or does the spec assume something not yet built? Flag any place the sub-menu concept under-specifies the menu-state transition.

6. **Scope discipline.** The spec defers Show Desktop (global Win+D) and the window-picker grid (option C). Confirm those are cleanly separable and not half-built by accident. Flag scope creep.

7. **Testability.** The spec's §7 lists unit tests. Are the proposed seams testable with the repo's conventions (NFluent, private nested fakes, no mocking lib, `Category=UI` excluded from CI)? Is the Maximize/Restore toggle logic extractable into a pure function so it can be unit-tested without Win32?
