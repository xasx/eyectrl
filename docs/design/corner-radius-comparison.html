Corner-radius unification — decision aid

Every mock below is drawn at the real size taken from source (device-independent pixels, so view at 100 % browser zoom for true scale) using the Midnight palette. Alpha is dropped — the two 0xFA surfaces are shown opaque — because this page is about geometry, not contrast. Purpose: decide the four open questions overlay-unification-spec.md §8 left open, before any XAML is touched.

Radius is purely cosmetic in this app. Gaze targets are registered as a centre point plus a physical radius (DwellTarget), not as the Border's geometry — so no value on this page can change how easy anything is to hit. That removes the accessibility risk from the decision and leaves it a visual one.

The concentric argument cuts against both. The usual design rule is child radius = parent radius − padding. The keyboard root is 8 with Padding="8", so the geometrically concentric key radius would be 0. Neither 6 nor 8 is principled here — which is an argument for choosing whichever needs fewer tokens, i.e. 8.

6. The circular close button — why the pill needs its own rule

QuickActionsGridWindow.xaml:21-24: a 44×44 Border at radius 22. Exactly half the size, so it is a circle, not a pill — the name in §8 is loose. Forcing it to 8 is the one change that genuinely breaks.

a large value, clamped by the renderer

The third cell is a claim that needs verifying before it becomes a token. CSS definitely clamps border-radius: 9999px to half the box, which is why it looks right above — this page is CSS, not WPF. Whether WPF's Border normalises an over-large CornerRadius the same way has not been checked against WPF here, and the spec must not assume it. Three ways to settle it, in the order I'd prefer them:
  1. Prove it headlessly — render a 44×44 Border at radius 22 and at 9999 to a RenderTargetBitmap on an STA test thread and compare corner pixels. If they match, CornerRadiusPill = 9999 becomes a real size-independent token. No window is shown and no input is simulated.
  2. Derive it at the site — the button is a fixed 44px, so 22 is really 44 / 2. Keep the literal and add a guard test that parses the XAML and asserts radius × 2 == Width, so a resize cannot silently leave it wrong.
  3. Exempt it — one documented literal in the guard's Exempt dictionary with the reason "circle, radius is half of a fixed 44px". Cheapest, and honest, but it protects nothing if the size changes.

10. Typography — the size scale the part that needs its own slice

67 FontSize sites, 17 distinct values (9, 10, 11, 12, 13, 14, 16, 18, 20, 22, 24, 28, 30, 32, 34, 36 plus 3 computed). More fragmented than the radii were. But the list is not one scale — it is two things tangled together.

Why a single ramp would be wrong

Roughly half these sites are glyphs sized to fit their container, not text:

Snapping those onto a text ramp resizes icons relative to the boxes they sit in — a visible regression, and backwards: ToolbarWindow already gets this right with _buttonSize * ButtonSymbolSizeRatio. So the scale work has to separate a text ramp from a glyph ratio rule, which is a structural distinction that does not exist in the codebase today.

26 sites grow, 2 shrink, 18 unchanged. There is no FontSizeCaption: at 12 it would have equalled FontSizeBody, and two names holding one value is the same fragmentation in a different coat. The 20/28/30 values leave the ramp entirely through the container-ratio rule below.

The clip risks this section originally warned about mostly evaporated — but only after every site was measured, which is why the warning was right to be there. Measured with the 1.33× line height:
  • QuickActions tile label — stays at 14. The wrapping risk never materialises.
  • Dwell controls 22→24 — auto-width, ≥70px tall. 31.92 fits in 70.
  • Keyboard key labels — leave the ramp for a container ratio, which also fixes a real bug: enlarging the keys today gives bigger keys with the same small letters.
  • Settings glyphs — were the worst case at +4px inside an 80px button; sizing them from their own container removes the risk rather than measuring it.

Neither is fixed by a layout change — if a site does not fit, its token assignment changes.
