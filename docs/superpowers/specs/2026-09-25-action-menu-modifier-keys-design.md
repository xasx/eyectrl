## Problem

Every mouse action EyeCtrl simulates is bare. `IInputSimulator`'s click and wheel methods carry no modifier state, the ring's `InteractionAction` has no modifier dimension, and a gaze-only user therefore cannot perform any of the ordinary held-modifier gestures a physical-mouse user does without thinking: Shift+click (range select), Ctrl+click (multi-select, open-in-new-tab), Alt+click (per-app semantics), Ctrl+wheel (browser zoom, Explorer icon scale). The keyboard half of this already exists — `ModifierKey` (`src/EyeCtrl.Core/Keyboard/ModifierKey.cs`), the keyboard's latched modifiers (`KeyboardViewModel.cs:68` field, `:70` copy-on-read property), atomic modified key sequences (`Win32InputSimulator.BuildModifiedKeySequence`) — but nothing connects it to the mouse path, and no UI offers a mouse modifier while the action menu is open.

Display and owner context for everything below: 3840×2400 physical at 200% = **1920×1200 DIP** (probed). Owner settings (read-only): `viewPosition: atCenter`, **`selectionMode: manualSelection`** — the owner's menu opens via the manual path (`ShowBack` true, `ManualSelectionActionMenuDwellMs`), `keySizeMultiplier: 1.5`, toolbar docked Top. Ring geometry: effectiveRingRadius = 125 + 70 + 60 = 255 DIP, menu-center clamp 255 + 70 = 325 DIP (`ActionMenuLayoutHelper.cs:32–35`); edge-button centers inset 30 + 50 + 10 = 90 DIP from an edge, radius `UIConstants.ButtonRadius` = 50.

## Behavior

While the action menu is open (normal and manual-selection path alike), the LEFT screen edge shows three dwell buttons — **Shift, Ctrl, Alt, top to bottom** — mirroring the right-edge Close/Help pair:

- Dwell a button → that modifier **latches** for the current menu session (visual latched state). Dwell it again → unlatches. Multiple modifiers can latch at once (Ctrl+Shift+click).
- **Re-arm rule (round-1 blocker fix, pinned by round 2):** after a toggle activation, that button's dwell target is removed — AFTER the activation's synchronous chain has fully returned — and re-added only once gaze has exited the target's **effective** hit radius. Holding gaze on a mod button toggles it exactly once; a one-sample flicker at the edge costs only dwell progress, never a toggle (mechanism 9 for the rules that make this true).
- Picking a ring action sends the latched set with the selection. The simulated input is **one atomic SendInput batch** per click: modifier key-down(s) → the mouse down/up event(s) → modifier key-up(s) in reverse. DoubleClick is ONE batch (mods↓, down, up, down, up, mods↑) — the exact event shape a physical user produces. When Alt is in the set, an unassigned menu-mask key (VK `0xE8`, the AutoHotkey `#MenuMaskKey` precedent) is injected down+up immediately before the Alt key-up so Alt-up alone can never drop the target app into menu-bar mode. A modified wheel batch leads with a MOVE|ABSOLUTE event: wheel events alone land at the current cursor position, and `ResetToFreeLook` re-enables the per-frame gaze `MoveCursor` across a doubly-deferred dispatch, so the cursor can drift before the wheel fires (`Win32InputSimulator.cs:86`, `GazeEngine.cs:597–601`).
- **Partial-send compensation (best-effort, stated honestly):** the send path observes the injected count; when 0 < sent < count, compensating events are sent — a mouse-up for each unmatched mouse-down (BEFORE the modifier ups), the menu-mask pair before a compensating Alt-up, and key-ups for modifiers whose down landed AND whose up did not (including a landed-but-unmatched mask down). A fully blocked batch (UIPI, sent = 0) injects nothing and needs none. Compensation itself can be blocked; that failure is logged by the same path — the design goal is "a partial send cannot silently weld modifiers down", not an absolute guarantee.
- Applies to the click family (Left/Right/Middle/Double) and the one-shot scroll family (Up/Down/Left/Right). **Modified scrolls send ONE wheel notch** — the four scroll arms map to (0,+1), (0,−1), (−1,0), (+1,0) with delta 1 when modified (ledger L9, with the owner-cost statement below).
- **Drag and ScrollMode are REFUSED while any modifier is latched** (ledger L8): the dwell completes, nothing fires, the menu stays open with the latch visibly still armed — and the refusal is MADE VISIBLE, not left to inference (round-2 Finding 1):
  - The dwell-completion cue is **suppressed for a refused activation** (per-activation flag read by `AnnounceDwellActivation` after `OnTargetActivated` returns — the base class reads it after the handler, so this works without touching the shared pin on opt-outs). A no-effect activation must not play the "dwell completed" cue — the repo's own contract (`DwellOverlayViewModelBase.cs:40–46`).
  - While the latch is non-empty, Drag and ScrollMode render **dimmed at the ring** — same slots, same geometry, so nothing moves under the gaze; the ring rebuilds only when the latch crosses the empty↔non-empty boundary, never on mod-set changes within it. The VM owns the boundary: `Receive(ToggleActionMenuModifierMessage)` bumps `RingVersion` on a crossing (the existing `RingVersion` branch in the binding coordinator then performs the rebuild); the coordinator's `LatchedModifiers` branch — which fires on EVERY toggle — only swaps the bar icons.
  - This matters most for this owner: their primary layer IS LeftClick, RightClick, DoubleClick, ScrollMode (`ActionMenuSettings.cs:42–43`) — the first "Scroll" they meet for "Ctrl+scroll" is the refused one, and under AtCenter the latch buttons at x = 90 are in peripheral vision from a ring item at x ≈ 635–720. "Nothing happened" must not look like a missed dwell.
- **One-shot lifecycle:** the latch exists only for the current menu opening — cleared on hide, reset on every show, toggles ignored while the menu is hidden (the deferred-hide race: the coordinator's hide is deferred twice, `OverlayMessageCoordinator.cs:158`, while the VM's runs synchronously). It survives More/BackToPrimary layer switches (`BuildLayer` does not touch it — pinned by test).

**Known geometry limits (recorded, follow-up material):** under AtGaze a ring item can overlap the mod buttons — the cited distances are CENTER-TO-CENTER, so the circles overlap deeply (up to ~80 DIP against radii 70 + 50). The same defect exists on the shipped right bar today. Separately and INDEPENDENT of ViewPosition: a menu opened over a visible keyboard puts the lower mod button near the keyboard's bottom-left keys (owner: bottom-docked keyboard at the 75%-height anchor, 1.5× keys), and a LEFT-docked toolbar (`ToolbarSettings.DockedEdge` supports Left, 120-DIP band) would sit directly under the mod bar. The owner runs AtCenter and Top-docked today, which dodges the first limit and the toolbar one but NOT the keyboard one. All three belong to one geometry pass (see Geometry limits).

## Mechanism

1. **Core — pass-through only** (`src/EyeCtrl.Core/Processing/InteractionManager.cs`): `OnActionSelected(InteractionAction action, IReadOnlySet<ModifierKey>? modifiers = null)`; the `ActionRequested` event gains the same trailing parameter. Core stores nothing and branches on nothing. BOTH raise sites pass it: the action-menu path (`:224`) forwards the parameter; the repeat-mode tick (`:362`) passes `null` (Core test pins that repeat ticks carry no modifiers). Production blast radius: one caller (`GazeEngineAdapter.cs:107`), one subscriber (`GazeEngineAdapter.cs:63`); the 15 test-subscriber lambdas across 6 files gain the third parameter (census verified exact by round 1).

2. **Messages** (`src/EyeCtrl.ViewModels/Messages/InteractionMessages.cs`): `ActionSelectedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`; new `ToggleActionMenuModifierMessage(ModifierKey Modifier)`; `ActionRequestedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`.

3. **The latch lives in `ActionMenuViewModel`**, mirroring the keyboard's precedent:
   - `Receive(ToggleActionMenuModifierMessage)` toggles and raises — **only when `IsVisible`**; a toggle deferred past a hide lands on a closed menu and is dropped.
   - `Receive(ShowActionMenuMessage)` resets the latch; `Receive(HideActionMenuMessage)` clears it.
   - **Capture means COPY:** `OnTargetActivated` snapshots `new HashSet<ModifierKey>(backing)` into the `ActionSelectedMessage` (the `KeyboardViewModel.cs:70` copy-on-read precedent). Handing the backing set by reference re-creates the ordering trap: `HideActionMenu` (`InteractionManager.cs:213`) is queued ahead of `ActionRequestedMessage` (`GazeEngineAdapter.cs:279–280` then `:334`), so an aliased set really would arrive empty.
   - **Refusal:** `OnTargetActivated` for Drag/ScrollMode with a non-empty latch sends nothing, sets the per-activation `_suppressAnnounce` flag (see Behavior), and returns; the item's dim state comes from `BuildLayer` reading the latch.

4. **Input layer** (`src/EyeCtrl.Core/Interfaces/IInputSimulator.cs`, `src/EyeCtrl.Platform/Input/Win32InputSimulator.cs`):
   - New default-interface-method overloads `LeftClick/RightClick/MiddleClick/DoubleClick(PhysicalPoint, IReadOnlySet<ModifierKey>?)` and `Scroll(PhysicalPoint, int, int, IReadOnlySet<ModifierKey>?)`, default bodies throwing `NotSupportedException` (the `MiddleClick` precedent, `IInputSimulator.cs:30`) — existing fakes compile, and a fake that actually receives a modified call fails loudly.
   - **Pure seam, characterization scoped to the real gap:** the wrapping is a new internal static pure builder `WrapWithModifiers(IReadOnlySet<ModifierKey>?, INPUT[] body)` — downs in `BuildModifiedKeySequence`'s order (Ctrl, Alt, Win, Shift; only Shift/Ctrl/Alt arrive), body, ups reversed, plus the Alt menu-mask pair. Two `BuildModifiedKeySequence` tests already exist (`Win32InputSimulatorClampTests.cs:37` no-modifier shape, `:49` Ctrl+Shift down-order/reversed-ups) — the characterization work extends coverage to **Alt, the Win extended flag, and extended main keys** BEFORE the extraction, not from zero.
   - `SendRaw` gains an `int` return (the injected count) so callers can observe short inserts; it remains the per-frame `MoveCursor` path (a return value costs nothing there). The new mouse overloads compose `WrapWithModifiers` output and send through `SendRaw`; on `0 < sent < count` the compensation of the Behavior paragraph is issued (mouse-ups first, then mask pair, then modifier key-ups — reverse-landed-order). `SendModifiedKeyPress` (which today calls `NativeMethods.SendInput` directly at `:155`) adopts the same `SendRaw` + compensation path — **this changes the shipped keyboard send path, so Task 1 carries keyboard regression coverage** (round-2 Finding 10).
   - `DoubleClick(pt, mods)` = ONE batch (down, up, down, up between the modifier pair). Null/empty modifiers ⇒ exactly the current byte stream — including `Scroll`'s existing two separate `SendInput` calls for the X/Y legs (`:84–95`) and the unmodified wheel's lack of a leading MOVE (pre-existing; follow-up 4).

5. **Dispatch** (`src/EyeCtrl.App/Services/Coordinators/KeyboardInteractionDispatcher.cs:143`): explicit routing — `mods is { Count: > 0 } ? simulator.X(pt, mods) : simulator.X(pt)`; the four scroll arms map to (0,+1), (0,−1), (−1,0), (+1,0), each with delta 1 on the modified arm (`DefaultScrollAmount = 3` stays for the unmodified arms). Never a blind nullable pass: with null it must behave byte-identically AND `TestFakes.FakeInputSimulator` (`TestFakes.cs:342`) does not implement the overloads. Throwing defaults catch stray calls; only recorded-modifier assertions catch dropped ones (Testing). The `Log.Information` line gains `Modifiers={Modifiers}`.

6. **Left-edge bar — second instance, not a subclass** (`EdgeButtonBarWindow`/`EdgeButtonBarViewModel` reused): the dwell registry is owner-keyed (`DwellDetectorRegistry.Register(object owner, …)`); both routers iterate the registration snapshot without keying by context (`DwellTimeRouter.cs:38`, `GeometryRouter.cs:49`). **DI shape:** the existing unkeyed `AddSingleton<EdgeButtonBarViewModel>()` (`AppBootstrapper.cs:381`, resolved at `:637`) stays as the right bar; exactly ONE keyed singleton is added for the mod bar — the repo's first keyed registration, fine on .NET 10. `IOverlayManager` gains `IEdgeButtonBar ActionMenuModBar` as a **default interface property whose default throws** — the six fakes keep compiling, and `TestFakes.PartialOverlayManager` (`TestFakes.cs:277`) gains an OPTIONAL mod-bar slot so `HideActionMenuBarOwnershipTests` (built via `MakeOverlayManager`, `:164–168`) can exercise the new paths (round-2 Finding 2). The positional `OverlayViewModels` record gains the member at both construction sites (`App.xaml.cs:198`, `AppBootstrapper.cs:627`) and the `ResolveViewModels` tuple (`App.xaml.cs:572–595`); `OverlayManager` builds/binds/wires a second `EdgeButtonBarWindow` exactly like the first (`:112`, `:138–154`).

7. **Definitions** (`src/EyeCtrl.App/Services/ActionMenuModifierButtons.cs`, new): three `EdgeButtonDefinition`s — ids `ActionMenu_mod_Shift` / `ActionMenu_mod_Ctrl` / `ActionMenu_mod_Alt`; `Activate` sends `ToggleActionMenuModifierMessage`; `RadiusLogical = UIConstants.ButtonRadius` (`UIConstants.cs:18`, NOT the ring's `ActionMenuButtonRadius`); labels always shown; dwell = the menu's ring dwell (`ShowBack ? ManualSelectionActionMenuDwellMs : ActionMenuDwellMs`); VerticalOffsets `0, ±(2·ButtonRadius + ManualSelectionSideButtonGap)` (`UIConstants.cs:37`), logical px converted with `DpiHelper.LogicalToPhysicalY` exactly like `ActionMenuEdgeButtons.cs:30–31` (`AddTarget` adds the offset to the anchor in physical space, `EdgeButtonBarViewModel.cs:107`).

8. **Show/hide placement (round-2 Finding 2 — fault isolation first):** both handlers run inside ONE shared try/catch today (`OverlayMessageCoordinator.cs:116–153`, `:160–189`); a mod-bar fault must not kill the right-bar hide (that guard is the strongest safety net in the app — a gaze-only user holding a pressed mouse button with nothing on screen to release it). Therefore: each bar gets its OWN try block, and in BOTH handlers the left bar is handled AFTER the right bar. Show: right-bar `ShowButtons` first (existing `:127–136`), then the left-bar show — still BEFORE the `ResolvedControl == null` early return at `:140` (appending at the end would never run in None mode). Hide: the right-bar ownership-guarded hide first (existing), then the left-bar hide — unconditionally (nothing else ever owns the left bar), outside the ownership `if` but inside its own try. Anchor via `ScreenGeometry.LeftEdgeAnchor(...)` — a new mirror of `RightEdgeAnchor` with a pure-arithmetic test overload (`ScreenGeometry.cs:40–51` pattern); inset 30 logical (each coordinator declares its own `RightEdgeInsetLogical` copy at `OverlayMessageCoordinator.cs:28` / `OverlayVmBindingCoordinator.cs:21`; a third lives on `KeyboardEdgeButtons`, `:30`). The SHOW path builds (mod-bar definitions, anchor) through one shared helper; the LATCH-REBUILD path does NOT use it (round-2 Finding 4) — it needs one definition and no anchor (mechanism 9).

9. **Latched visual = in-place swap + exit-before-re-arm (round-1 F1 blocker; rules pinned by round 2):**
   - **The binding branch (round-2 Finding 4):** the `LatchedModifiers` listener is hosted in `OverlayVmBindingCoordinator.OnActionMenuVMPropertyChanged` (`:282–316`, where the other ActionMenuVM branches live) as a SEPARATE `else if` on `LatchedModifiers`, guarded on `IsVisible` — clearing the latch during hide must not re-show the bar. It is never folded into the `RingVersion`/`ShowLabels` condition (`:306–308`) that calls `ShowActionMenu()` and would re-run the screen capture; the branch's whole body is a `ReplaceButton` per mod id.
   - `EdgeButtonBarViewModel` gains `ReplaceButton(string id, EdgeButtonDefinition definition)`: swaps the `_definitions` entry (no-op when the id is missing — bar hidden, or a reset firing before the deferred show), raises `ButtonSetChanged`, and touches NOTHING else. `EdgeButtonState` has no icon state to update (`EdgeButtonState.cs:11–15`); `SyncButtons` re-reads `DefinitionFor(id).Icon` (`EdgeButtonBarWindow.xaml.cs:92–96`), so the redraw picks the variant up with detector state intact. Using `ShowButtons` here is the round-1 blocker: it `ResetCooldown()`s (`EdgeButtonBarViewModel.cs:44`), and since the detector clears `IsGazeInside`/`EnteredTimestamp` on every activation (`DwellDetector.cs:382–384`) and the toggle chain is synchronous, a held gaze would re-toggle at dwell cadence.
   - **Exit-before-re-arm, five rules:** (a) the target is removed **AFTER `def.Activate(Messenger)` returns** — `DwellDetector.AddTarget` replaces by id (`:108–115`), so removing first would lose to any re-add inside the synchronous toggle chain; removal after it wins. Consequence: the mutation "use `ShowButtons` instead of the replace" is MASKED by the re-arm, so its regression test must be at the call site and observe a state ShowButtons alone would change: the bar's cooldown surviving the toggle (after a toggle, an immediate re-dwell of another bar button is still cooldown-gated — `ShowButtons`'s `ResetCooldown` would have un-gated it). (b) Pending re-arms are cleared in `ShowButtons`, `Hide` AND `RemoveButton`. (c) The exit test uses the removed `DwellTarget`'s **effective** radius — the geometry router can add up to `GeometryMaxMarginPx` (owner: 100 px physical, `GeometryRouter.cs:52–58`) — never `def.RadiusLogical`; an exit test on the base radius would re-arm while gaze is still inside the enlarged hit area. No hysteresis is required: a flicker outside the effective radius costs one re-arm, and re-dwelling still needs the full dwell time inside. (d) Re-add goes through `DwellDetector.AddTarget` directly — the VM's private `AddTarget` also does `Buttons.Add` and would duplicate the button state (`EdgeButtonBarViewModel.cs:104–112`). (e) The bar VM's new gaze-sample `Receive` override routes through `SampleMayDwell` per the base-class contract (`DwellOverlayViewModelBase.cs:80–87`).
   - `EdgeButtonDefinition` gains a `RearmOnGazeExit` flag (default false); the mod-bar definitions set it. (The right bar's Help toggle shares the no-re-arm exposure today — filed follow-up 2, not fixed here.)
   - Icons: three new `ActionIcon` values (Shift, Ctrl, Alt) plus latched variants. The latched variant's PRIMARY cue is a **rim drawn in the icon geometry** — committed, because `IconGeometry` has no thickness parameter and every icon strokes at the shared `GridStrokeThickness` (`ActionIcons.cs:44–45`); a thicker stroke would be a shared-control change, contradicting "zero shared-control changes". The filled margin dot stays as a secondary cue (the peripheral-vision rule, `ActionIcons.cs:23–27`, is why the dot cannot be the primary cue). Deliberately NOT an accent ring/fill on `DwellArcButton`: the dwell-progress arc is already `BrushAccent` (`DwellArcButton.cs:167`), and a fill state invites the dwell-blend contrast collapse.

10. **Capture hygiene (round-1 F14):** `EdgeButtonBarWindow`'s constructor sets `ExcludeFromScreenCapture = true` (compare `ActionMenuWindow.xaml.cs:53` — an init-only property settable from a derived constructor). The exposure is real on the manual-selection path, where the capture centers on the unclamped `ManualSelectionCenter` (`ActionMenuWindow.xaml.cs:81–84`); one line fixes both bars.

## Pause interplay

The mod bar inherits `EdgeButtonBarViewModel.DwellActiveWhilePaused => true` (release-affordance semantics). A paused session cannot have an open menu (`TogglePause` hides it, `InteractionManager.cs:284`), the latch resets on show and ignores toggles while hidden, and the new gaze-sample override gates on `SampleMayDwell` — no pause hole. Latch toggling itself is OS-input-free.

## Geometry limits (recorded; follow-ups, not v1 work)

- **AtGaze ring overlap:** a default 5-item ring's leftmost item lands ~7.5–42 DIP from a mod-button CENTER (center-to-center; the circles overlap by up to ~80 DIP against radii 70 + 50). Both are live dwell targets on independent detectors — no z-order arbiter exists. The shipped right bar has the same defect today (RightClick item ~20 DIP center-to-center from Close). Fix belongs to a dedicated geometry pass (widen the clamp to clear both bar bands) — follow-up 1.
- **Keyboard overlap (ViewPosition-independent):** the mod bar sits at 50% height ±120 DIP regardless of ViewPosition; the owner's bottom-docked keyboard anchors at 75% height with 1.5× keys, so the lower mod button plausibly overlaps its left keys (which include the keyboard's own Ctrl latch). Plausible, not measured — same geometry pass, follow-up 1.
- **Left-docked toolbar:** `ToolbarSettings.DockedEdge` supports Left (120-DIP band) which would sit directly under the mod bar; the owner docks Top. Recorded in the same pass.

## Implementation order (round-2 Finding 10 split adopted)

1. Platform: extend `BuildModifiedKeySequence` characterization → `WrapWithModifiers` + `SendRaw` returning count + partial-send compensation + menu-mask key + modified-wheel leading MOVE + **keyboard-path regression coverage**.
2. Core + messages + adapter pass-through, including the repeat-mode raise site and the 15 test lambdas.
3. ViewModel latch (copy-on-capture, show/hide hygiene, refusal + cue suppression + dim-state read).
4a. ViewModels bar mechanics: `RearmOnGazeExit` flag, `ReplaceButton`, the four re-arm rules, headless held-gaze + call-site tests.
4b. App wiring: bar instance, coordinators (own try blocks, left-after-right), DI, `IOverlayManager` + `PartialOverlayManager` slot, icons (Core + Controls), `ExcludeFromScreenCapture`.
5. Dispatcher routing and logging.

## Out of scope (v1, recorded escape hatches)

- **Ctrl + gaze ScrollMode / modifier-wrapped Drag** — held-modifier sessions need down-on-entry/up-on-every-exit-path machinery; v2 candidates. Until then they are REFUSED while latched (L8), visibly and cue-silently.
- **Settings toggle** for the mod bar — always shown while the menu is open, like Close/Help.
- **Win modifier** on the bar — no common Win+mouse gesture; the keyboard's Win covers chords.
- **Ring relabeling** ("Shift + Left click") while latched — the mod button and the dimmed ring items are the feedback surfaces.
- **AtGaze / keyboard / left-toolbar overlap fixes** — dedicated geometry pass.
