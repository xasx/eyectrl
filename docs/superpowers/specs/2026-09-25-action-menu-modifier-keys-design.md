## Problem

Every mouse action EyeCtrl simulates is bare. `IInputSimulator`'s click and wheel methods carry no modifier state, the ring's `InteractionAction` has no modifier dimension, and a gaze-only user therefore cannot perform any of the ordinary held-modifier gestures a physical-mouse user does without thinking: Shift+click (range select), Ctrl+click (multi-select, open-in-new-tab), Alt+click (per-app semantics), Ctrl+wheel (browser zoom, Explorer icon scale). The keyboard half of this already exists — `ModifierKey` (`src/EyeCtrl.Core/Keyboard/ModifierKey.cs`), the keyboard's latched `ActiveModifiers` (`KeyboardViewModel.cs:68`), atomic modified key sequences (`Win32InputSimulator.BuildModifiedKeySequence`) — but nothing connects it to the mouse path, and no UI offers a mouse modifier while the action menu is open.

Display reference for all geometry below: the box runs 3840×2400 physical at 200% scaling = **1920×1200 DIP** (`SystemParameters.PrimaryScreenWidth/Height` probed 1920×1200). Ring geometry: `ActionMenuLayoutHelper` clamps the menu center so `effectiveRingRadius + ActionMenuButtonRadius` (default 255 + 70 = 325 DIP) fits on screen; edge buttons of radius `UIConstants.ButtonRadius` (50) sit inset 30 + 50 + 10 = 90 DIP from an edge.

## Behavior

While the action menu is open (normal and manual-selection path alike), the LEFT screen edge shows three dwell buttons — **Shift, Ctrl, Alt, top to bottom** — mirroring the right-edge Close/Help pair:

- Dwell a button → that modifier **latches** for the current menu session (visual latched state). Dwell it again → unlatches. Multiple modifiers can latch at once (Ctrl+Shift+click).
- **Re-arm rule (round-1 blocker fix):** after a toggle activation, that button is removed from the dwell detector and only returns once gaze has EXITED its radius. Holding gaze on a mod button toggles it exactly once — never a latch/unlatch flutter at dwell cadence.
- Picking a ring action sends the latched set with the selection. The simulated input is **one atomic SendInput batch** per click: modifier key-down(s) → the mouse down/up event(s) → modifier key-up(s) in reverse. DoubleClick is ONE batch (mods↓, down, up, down, up, mods↑) — the exact event shape a physical user produces, so no "does Windows track double-click across keyboard events" claim is needed. When Alt is in the set, an unassigned menu-mask key (VK `0xE8`, the AutoHotkey `#MenuMaskKey` precedent) is injected down+up immediately before the Alt key-up so Alt-up alone can never drop the target app into menu-bar mode.
- **Partial-send compensation:** if `SendInput` reports a short insert (0 < sent < count — the UIPI block case injects nothing and needs none), compensating key-ups are sent for every modifier whose down landed inside the injected prefix (and a mouse-up if a mouse-down landed). A blocked batch must never leave Ctrl welded down for a user with no physical keyboard to clear it.
- Applies to the click family (Left/Right/Middle/Double) and the one-shot scroll family (Up/Down/Left/Right). **Modified scrolls send ONE wheel notch** (delta 1), not the unmodified `DefaultScrollAmount = 3` — zoom surfaces step per wheel event, and 3 notches per menu cycle would overshoot (ledger L9).
- **Drag and ScrollMode are REFUSED while any modifier is latched** (ledger L8, flipped by round 1): the dwell completes, nothing fires, the menu stays open with the latch visibly still armed. Rationale: Ctrl+Drag silently becoming a move in Explorer is a destructive surprise; a refused activation is inherent feedback (nothing closed, latch still shown). Keyboard and PinNote proceed as today and consume the latch with the menu.
- **One-shot lifecycle:** the latch exists only for the current menu opening. It is cleared on hide AND reset on every show (the `ShowLabels` precedent, `ActionMenuViewModel.cs:66`/:162); `ToggleActionMenuModifierMessage` is a no-op while the menu is not visible, so a toggle deferred past a hide cannot arm an invisible latch for the next open. It survives More/BackToPrimary layer switches (`BuildLayer` does not touch it — pinned by test).

**Known geometry limits (recorded, not fixed here — see Geometry limits):** under ViewPosition AtGaze a ring item can overlap the mod buttons, exactly as the shipped right-edge bar already overlaps the ring today; and a menu opened over a visible keyboard puts the lower mod button near the keyboard's bottom-left keys (which include the keyboard's own Ctrl latch). The owner runs AtCenter (verified in `settings.json`), so neither is reachable for them today; both are follow-up material, not v1 blockers.

## Mechanism

1. **Core — pass-through only** (`src/EyeCtrl.Core/Processing/InteractionManager.cs`): `OnActionSelected(InteractionAction action, IReadOnlySet<ModifierKey>? modifiers = null)`; the `ActionRequested` event gains the same trailing parameter. Core stores nothing and branches on nothing. BOTH raise sites pass it: the action-menu path (`:224`) forwards the parameter; the repeat-mode tick (`:362`) passes `null` — a compile-forced change the spec now names, with a Core test pinning that repeat ticks carry no modifiers. Production blast radius: one caller (`GazeEngineAdapter.cs:107`), one subscriber (`GazeEngineAdapter.cs:63`); the 15 test-subscriber lambdas across 6 files gain the third parameter (census in rev 1, verified exact by round 1).

2. **Messages** (`src/EyeCtrl.ViewModels/Messages/InteractionMessages.cs`): `ActionSelectedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`; new `ToggleActionMenuModifierMessage(ModifierKey Modifier)`; `ActionRequestedMessage` gains `IReadOnlySet<ModifierKey>? Modifiers = null`.

3. **The latch lives in `ActionMenuViewModel`**, mirroring the keyboard's `_activeModifiers` precedent: a backing `HashSet<ModifierKey>` + an observable `LatchedModifiers`. Rules:
   - `Receive(ToggleActionMenuModifierMessage)` toggles and raises — **but only when `IsVisible`**; a toggle deferred past a hide lands on a closed menu and is dropped.
   - `Receive(ShowActionMenuMessage)` resets the latch (fresh open starts unlatched) — the hide-clear alone leaves a dispatcher-turn race (round-1 F10: the bar's hide is deferred, so a toggle can land after the hide-clear).
   - `Receive(HideActionMenuMessage)` clears.
   - **Capture means COPY:** `OnTargetActivated` snapshots `new HashSet<ModifierKey>(backing)` into the `ActionSelectedMessage` (the `KeyboardViewModel.cs:70` copy-on-read precedent). Handing the backing set by reference re-creates the ordering trap: `InteractionManager.OnActionSelected` fires `HideActionMenu` (`:213`) before `ActionRequested` (`:224`), the hide reaches the VM first and `Clear()`s the very set the message carries.
   - Refusal: `OnTargetActivated` for Drag/ScrollMode with a non-empty latch sends nothing (menu stays open — see Behavior).

4. **Input layer** (`src/EyeCtrl.Core/Interfaces/IInputSimulator.cs`, `src/EyeCtrl.Platform/Input/Win32InputSimulator.cs`):
   - New default-interface-method overloads `LeftClick/RightClick/MiddleClick/DoubleClick(PhysicalPoint, IReadOnlySet<ModifierKey>?)` and `Scroll(PhysicalPoint, int, int, IReadOnlySet<ModifierKey>?)`, default bodies throwing `NotSupportedException` (the `MiddleClick` precedent, `IInputSimulator.cs:30`) — existing fakes compile, and a fake that actually receives a modified call fails loudly.
   - **Pure seam first (round-1 F13):** the modifier wrapping is a new internal static pure builder `WrapWithModifiers(IReadOnlySet<ModifierKey>?, INPUT[] body)` — downs in `BuildModifiedKeySequence`'s order (Ctrl, Alt, Win, Shift; only Shift/Ctrl/Alt arrive), body, ups reversed, plus the Alt menu-mask pair described under Behavior. `CreateMouseInput` is instance-bound (coordinate mapper + `GetSystemMetrics`), so the WRAPPER is the testable unit. **A characterization test of `BuildModifiedKeySequence`'s current output is committed BEFORE the extraction** — it has zero tests today, so "byte-identical to the old inline sequence" is otherwise unprovable.
   - The new mouse overloads compose `WrapWithModifiers` output and send through `SendRaw` — not a direct `SendInput` — so partial sends are observed; on `0 < sent < count` the compensating key-ups of mechanism item 4's Behavior paragraph are issued. `SendModifiedKeyPress` (which today calls `NativeMethods.SendInput` directly at `:155`, bypassing even the log) adopts the same `SendRaw` + compensation path.
   - `DoubleClick(pt, mods)` = ONE batch (down, up, down, up between the modifier pair). Null/empty modifiers ⇒ exactly the current byte stream — including `Scroll`'s existing two separate `SendInput` calls for the X/Y legs (`:84–95`).

5. **Dispatch** (`src/EyeCtrl.App/Services/Coordinators/KeyboardInteractionDispatcher.cs:143`): the routing rule is explicit — `mods is { Count: > 0 } ? simulator.X(pt, mods) : simulator.X(pt)` — never a blind pass of a nullable into the overload: with null it must behave byte-identically AND the existing `TestFakes.FakeInputSimulator` (`TestFakes.cs:342`) does not implement the overloads. For the scroll arms the modified call ALSO changes the delta to one notch — `Scroll(pt, 0, 1, mods)` / `Scroll(pt, 1, 0, mods)` (ledger L9), the unmodified arms keep `DefaultScrollAmount = 3`. A throwing default catches a fake receiving an unexpected modified call; it does NOT catch a dropped modifier — only assertions on recorded modifiers do (Testing). The `Log.Information` line gains `Modifiers={Modifiers}`.

6. **Left-edge bar — second instance, not a subclass** (`EdgeButtonBarWindow`/`EdgeButtonBarViewModel` reused): the dwell registry is owner-keyed (`DwellDetectorRegistry.Register(object owner, …)`); both routers iterate the registration snapshot without keying by context (`DwellTimeRouter.cs:38`, `GeometryRouter.cs:49`), so two live `DwellContext.EdgeButtonBar` registrations coexist. **DI shape (round-1 F9):** the existing unkeyed `AddSingleton<EdgeButtonBarViewModel>()` (`AppBootstrapper.cs:381`, resolved at `:637`) stays as the right bar; exactly ONE keyed singleton is added for the mod bar — re-keying both would churn every existing resolution. `IOverlayManager` gains `IEdgeButtonBar ActionMenuModBar` as a **default interface property whose default throws** — the six test fakes that implement the interface (`EdgeButtonBarZOrderTests.cs:242`, `ManualSelectionAnchorWiringTests.cs:93`, `ManualSelectionRecaptureTests.cs:192`, `TaskSwitcherReArmTests.cs:176`, `TestFakes.cs:277`, `ToolbarVisibilityAdapterTests.cs:409`) keep compiling. The positional `OverlayViewModels` record gains the member at both construction sites (`App.xaml.cs:198`, `AppBootstrapper.cs:627`) and the `ResolveViewModels` tuple (`App.xaml.cs:572–595`); `OverlayManager` builds/binds/wires a second `EdgeButtonBarWindow` exactly like the first (`:112`, `:138–154`).

7. **Definitions** (`src/EyeCtrl.App/Services/ActionMenuModifierButtons.cs`, new): three `EdgeButtonDefinition`s — ids `ActionMenu_mod_Shift` / `ActionMenu_mod_Ctrl` / `ActionMenu_mod_Alt`; `Activate` sends `ToggleActionMenuModifierMessage`; `RadiusLogical = UIConstants.ButtonRadius` (the Close/Help size — `UIConstants.cs:18`, NOT the ring's `ActionMenuButtonRadius`); labels always shown ("Shift" / "Ctrl" / "Alt" — the `ActionMenuEdgeButtons` convention); dwell = the menu's ring dwell (`ShowBack ? ManualSelectionActionMenuDwellMs : ActionMenuDwellMs`); VerticalOffsets `0, ±(2·ButtonRadius + ManualSelectionSideButtonGap)` (`UIConstants.cs:37`), logical px converted with `DpiHelper.LogicalToPhysicalY` exactly like `ActionMenuEdgeButtons.cs:30–31` (`AddTarget` adds the offset to the anchor in physical space, `EdgeButtonBarViewModel.cs:107`).

8. **Show/hide placement (round-1 F7 — the placement IS the finding):** in `OverlayMessageCoordinator`, the left-bar show goes into the `ShowActionMenuMessage` handler (`:113–154`) **BEFORE the `if (msg.ResolvedControl == null) return;` at `:140`** — appended at the end, it would only ever run when AutoSelection resolved a control, i.e. never in None mode. The left-bar hide goes into the `HideActionMenuMessage` handler (`:156–190`) **FIRST, outside the right-bar ownership guard** — drag/scroll/keyboard contexts steal the right bar mid-flight (repeat cannot: `EnterRepeatMode` is FreeLook-guarded, `InteractionManager.cs:315`; the keyboard can, `KeyboardCoordinator.cs:386–393`), and nothing else ever owns the left bar. Anchor via `ScreenGeometry.LeftEdgeAnchor(...)` — a new mirror of `RightEdgeAnchor` with a pure-arithmetic test overload (`ScreenGeometry.cs:40–51` pattern); inset 30 logical, mirroring `RightEdgeInsetLogical` (each coordinator declares its own copy at `OverlayMessageCoordinator.cs:28` / `OverlayVmBindingCoordinator.cs:21`; a third lives on `KeyboardEdgeButtons.RightEdgeInsetLogical` — the new anchor takes the inset as a parameter and the call site reuses the coordinator's 30). One shared helper builds (definitions, anchor) for BOTH the show path and the latch-rebuild path so they cannot drift (round-1 F11).

9. **Latched visual = in-place swap + re-arm rule, zero shared-control changes** (round-1 F1 blocker + F15):
   - `EdgeButtonBarViewModel` gains a targeted replace method (replaces the `_definitions` entry, updates the `EdgeButtonState`, raises `ButtonSetChanged`) that does NOT call `ClearTargets`/`RemoveTarget`/`ResetCooldown` — `SyncButtons` already re-reads `DefinitionFor(id).Icon` (`EdgeButtonBarWindow.xaml.cs:92–96`), so the redraw picks the variant up with detector state intact. Using `ShowButtons` here is the blocker: it `ResetCooldown()`s (`EdgeButtonBarViewModel.cs:44`), and since the detector clears `IsGazeInside`/`EnteredTimestamp` on every activation (`DwellDetector.cs:384` region) and the whole toggle chain is synchronous, a held gaze would re-toggle at dwell cadence forever.
   - **Exit-before-re-arm** rides the same activation: `EdgeButtonDefinition` gains a `RearmOnGazeExit` flag (default false); the bar VM, on activating a flagged target, removes it from the detector and re-adds it when the gaze sample (which the base class already receives) leaves the target's radius. Even with the cooldown kept, held gaze re-fires every ~1 s — only exit-based re-arming makes "toggle exactly once" true. (The right bar's Help toggle shares this exposure today — filed follow-up, not fixed here.)
   - Icons: three new `ActionIcon` values (Shift, Ctrl, Alt) plus latched variants. The latched variant's PRIMARY cue is outline-level — a thicker `BrushTextPrimary` stroke or a rim — because the icon set's own rule (`ActionIcons.cs:23–27`) is that a mark inside the same silhouette is invisible in peripheral vision, which is where a gaze user finds a target; the filled margin dot stays as a secondary cue. Deliberately NOT an accent ring/fill on `DwellArcButton`: the dwell-progress arc is already `BrushAccent` (`DwellArcButton.cs:167`), and a fill state invites the dwell-blend contrast collapse (visual-assessment trap).

10. **Capture hygiene (round-1 F14):** `EdgeButtonBarWindow`'s constructor sets `ExcludeFromScreenCapture = true` (compare `ActionMenuWindow.xaml.cs:53`). Today the action-menu preview can bake the right-edge buttons into the captured circle; with a left bar the exposure doubles. One line fixes both bars.

## Pause interplay

The mod bar inherits `EdgeButtonBarViewModel.DwellActiveWhilePaused => true` (release-affordance semantics). A paused session cannot have an open menu (`TogglePause` hides it, `InteractionManager.cs:284`), and the latch resets on show and ignores toggles while hidden (mechanism item 3), so the deferred-hide race cannot arm a paused latch either. Latch toggling itself is OS-input-free.

## Geometry limits (recorded; follow-ups, not v1 work)

- **AtGaze ring overlap (round-1 F8):** with the menu center clamped to ≥325 DIP from an edge, a default 5-item ring's leftmost item lands ~40 DIP from the upper or lower mod button (button centers at x=90; radii 70+50). Both are live dwell targets on independent detectors — no z-order arbiter exists, so both would fire. The SHIPPED right-edge bar has the same defect today (the RightClick item sits ~20 DIP from Close). The owner runs AtCenter (verified read-only in `settings.json`). Fix belongs to a dedicated geometry pass (widen the clamp to clear both bar bands) — filed follow-up, covering right and left bars.
- **Keyboard overlap (round-1 F16):** a menu opened over a visible keyboard puts the lower mod button near the keyboard's bottom-left keys. Same class, same follow-up. The spec accepts both explicitly rather than widening the clamp inside this feature (ring-clamp changes reflow every menu open and deserve their own review).

## Out of scope (v1, recorded escape hatches)

- **Ctrl + gaze ScrollMode / modifier-wrapped Drag** — held-modifier sessions need down-on-entry/up-on-every-exit-path machinery; v2 candidates. Until then they are REFUSED while latched (L8), never silently dropped.
- **Settings toggle** for the mod bar — always shown while the menu is open, like Close/Help.
- **Win modifier** on the bar — no common Win+mouse gesture; the keyboard's Win covers chords.
- **Ring relabeling** ("Shift + Left click") while latched — the mod button is the feedback surface.
- **AtGaze/keyboard overlap fixes** — dedicated geometry pass (see Geometry limits).
